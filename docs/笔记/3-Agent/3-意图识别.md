### 三路投票

意图识别与编排：融合 LLM Few-shot、字符 n-gram 相似度和关键词规则三路投票，输出意图、置信度与实体，低置信度先追问澄清；再按意图和实体对主/辅 Agent 打分路由，复合问题并行处理后返回路由原因与置信度

这三路是同一个分类问题的三种解法，互补关系是：**模型负责「这句话属于哪类」，字面负责「像不像模板」，规则负责「把粗粒度修细」**。

## 1. LLM Few-shot

**做法**：

```java
// pudding-java\src\main\java\com\pudding\intent\IntentRecognizer.java
private Map<String, Object> llmRecognize(String message, List<Map<String, String>> history) {
        StringBuilder examples = new StringBuilder();
        TEMPLATES.forEach((intent, samples) ->
                examples.append("消息: \"").append(samples.getFirst()).append("\" -> 意图: ")
                        .append(intent.name().toLowerCase(Locale.ROOT)).append('\n'));
        String prompt = """
                你是客服意图分析专家。根据示例判断用户意图，返回 JSON。
                如果用户问题能匹配细粒度业务意图，请优先返回细粒度意图，而不是宽泛大类。
                例如退款优先返回 refund，发票优先返回 invoice，登录故障优先返回 technical_login。
                示例:
                %s
                最近对话:
                %s
                用户消息: "%s"
                返回格式: {"intent":"technical","confidence":0.9,"reasoning":"一句话说明"}
                可选意图: %s
                """.formatted(examples, history == null ? "" : history, message, allIntentNames());
        try {
            String raw = llmGateway.chat("", prompt, 0.1, 256);
            String json = sliceJsonObject(raw);
            Map<String, Object> data = objectMapper.readValue(json, new TypeReference<>() {
            });
            data.put("intent", parseIntent(String.valueOf(data.get("intent"))));
            return data;
        } catch (Exception ex) {
            Map<String, Object> fallback = new HashMap<>();
            fallback.put("intent", IntentCategory.OTHER);
            fallback.put("confidence", 0.0);
            fallback.put("reasoning", "LLM recognition failed");
            fallback.put("failed", true);
            return fallback;
        }
    }
```

```text
系统提示：你是客服意图分析专家，根据示例判断，返回 JSON
示例：每个意图取第一条模板，拼成「消息: "..." -> 意图: xxx」，共 18 条
最近对话：最近几条历史（帮助理解「那退款呢」这种省略句）
用户消息 + 全部 19 个可选意图名
```

调用参数 `temperature=0.1, max_tokens=256`，模型返回：

```json
{"intent":"technical_login","confidence":0.9,"reasoning":"用户登录报401"}
```

解析失败或超时 → `{intent: OTHER, confidence: 0, failed: true}`，交给后面两路兜底。

**为什么用它**：语义理解最强，能处理「钱怎么还没退回来」这种没有一个关键词对得上的说法；Few-shot 的主要作用是**固定输出格式**和**给边界样例**。

**局限**：每类只有 1 条示例，覆盖窄；一次网络调用，几百毫秒；模型可能吐出枚举外的值，`parseIntent` 会兜底成 OTHER。

## 2. 字符 n-gram 相似度

**做法**：

```java
    private Map<String, Object> semanticRecognize(String message) {
        IntentCategory best = IntentCategory.OTHER;
        double bestScore = 0.0;
        for (Map.Entry<IntentCategory, List<String>> entry : TEMPLATES.entrySet()) {
            for (String sample : entry.getValue()) {
                double score = jaccard(charNgrams(message), charNgrams(sample));
                if (score > bestScore) {
                    bestScore = score;
                    best = entry.getKey();
                }
            }
        }
        return Map.of("intent", best, "confidence", bestScore);
    }

```



```text
1. 消息转小写、去首尾空格
2. 切成 1 字、2 字、3 字的片段，放进集合去重
   例："退款多久" → {退, 款, 多, 久, 退款, 款多, 多久, 退款多, 款多久}
3. 和 18 个意图 × 每类 3 条模板逐条算 Jaccard：
   Jaccard = 交集大小 / 并集大小
4. 取最高分那条模板对应的意图
```

纯本地字符串运算，**零网络、零成本、可复现**。

**为什么是字符而不是词**：中文没有空格，分词器本身就是一个依赖和误差源；1–3 字的 n-gram 能近似覆盖「词」和「短语」，还顺带容忍少量语序变化。

**局限**：只认字面重叠。用户说「钱什么时候退回来」，模板是「退款多久到账」，共享的 n-gram 很少，分数会很低。而且长句和短模板做 Jaccard 会被并集稀释，越啰嗦分越低。

## 3. 关键词规则

**做法**：分两层，**细粒度优先**。

```text
第一层：9 个细粒度意图（订单状态/物流/退款/发票/支付问题/账户安全/登录/崩溃/转人工）
        命中就立刻返回，不再看第二层
第二层：8 个粗粒度意图（投诉/抱怨/查询/请求/问候/账单/技术/账户）
```

打分公式：

```java
// pudding-java\src\main\java\com\pudding\intent\IntentRecognizer.java 
private Map<String, Object> bestPatternMatch(String msg, Map<IntentCategory, List<String>> patterns) {
        IntentCategory best = IntentCategory.OTHER;
        double bestScore = 0.0;
        for (Map.Entry<IntentCategory, List<String>> entry : patterns.entrySet()) {
            long hits = entry.getValue().stream().filter(msg::contains).count();
            if (hits > 0) {
                double score = Math.min(1.0, 0.5 + 0.25 * (hits - 1));
                if (score > bestScore) {
                    bestScore = score;
                    best = entry.getKey();
                }
            }
        }
        return Map.of("intent", best, "confidence", bestScore);
    }
```

```text
score = min(1.0, 0.5 + 0.25 × (命中词数 - 1))
1 个词 → 0.5     2 个词 → 0.75     3 个及以上 → 1.0
```

**它的真正价值不只是那 0.1 的权重，而是「修细」**：

```text
如果融合后的意图是粗粒度（如 TECHNICAL）
且规则命中了细粒度意图（如 TECHNICAL_LOGIN）
且规则置信度 ≥ 0.5
且当前最高分 < 0.8          ← 0.7×conf 最大只有 0.7，恒成立
→ 用细粒度覆盖
```

所以「登录一直 401」这种句子，模型给 `technical`，规则会把它修成 `technical_login`。代价是：**句子里只要出现细粒度关键词，规则几乎总会盖过模型的粗分类**，关键词表的维护质量直接决定细分类准确率。

## 三路怎么合

```text
scores[意图] += 0.70 × LLM置信度
             + 0.20 × n-gram置信度
             + 0.10 × 规则置信度
取最高分 → 修细 → 若仍 < 0.5 判 OTHER
LLM 失败时特殊：直接用 n-gram，其次规则，不走加权
```

举个「登录 401」的例子：

| 路       | 输出                        | 置信度   | 加权贡献    |
| -------- | --------------------------- | -------- | ----------- |
| LLM      | technical_login             | 0.90     | 0.63        |
| n-gram   | technical_login             | 0.35     | 0.07        |
| 规则     | technical_login（命中 401） | 0.50     | 0.05        |
| **合计** | **technical_login**         | **0.75** | 过 0.5 阈值 |

## 一个必须知道的结论

**「三路投票」里只有一路是模型。** 另外两路是本地字符串运算，而且没有归一化——规则路满分 0.1、n-gram 满分 0.2，单靠它们过不了 0.5。所以真实机制是：

> **LLM 决定「够不够格」，关键词决定「细不细」，n-gram 补「常不常见」。**

## 面试版（40 秒）

> 第一路是 LLM Few-shot：每个意图给一条示例，让它返回 JSON 的 intent 和 confidence，权重 0.7，负责语义。
> 第二路是字符 n-gram：把句子拆成 1 到 3 字片段，和 54 条模板算 Jaccard 相似度，取最高，权重 0.2，纯本地运算，负责补常见表达。
> 第三路是关键词规则：细粒度关键词优先，命中就返回，权重只有 0.1，但它的作用是兜底和把粗粒度修成细粒度。
> 三路加权后取最高，低于 0.5 判成 OTHER。所以要澄清的是，这里只有一路是模型，另外两路是字符串运算，而且因为没有归一化，单靠后两路过不了阈值。

低置信度澄清由`leaderAgent`负责

## 一、「输出实体」是什么

实体 = 从用户这句话里**抽出来的结构化参数**，和意图一起返回，代码在。

```java
Map<String, Object> llm = llmRecognize(message, history);
Map<String, Object> semantic = semanticRecognize(message);
Map<String, Object> pattern = patternRecognize(message);
VoteResult vote = vote(llm, semantic, pattern);
IntentCategory intent = vote.intent();
UrgencyLevel urgency = urgency(message, intent);
IntentResult result = new IntentResult(
        intent,
        vote.confidence(),

```

具体的实体抽取如下：

```java
// pudding-java\src\main\java\com\pudding\intent\IntentRecognizer.java 
private Map<String, List<String>> extractEntities(String message) {
        Map<String, List<String>> entities = new LinkedHashMap<>();
        entities.put("order_id", regexFindGroup(message, "(?:订单号?|order(?:_id)?|#)\\s*[:：#]?\\s*([A-Za-z0-9_-]{4,32})", 1));
        entities.put("product", List.of());
        entities.put("date", regexFind(message, "(今天|明天|昨天|本周|这周|下周|\\d{4}[-/.年]\\d{1,2}[-/.月]\\d{1,2}日?)"));
        entities.put("error_code", regexFind(message, "\\b[45]\\d{2}\\b"));
        entities.put("amount", regexFind(message, "((?:¥|￥)\\s*\\d+(?:\\.\\d{1,2})?|\\d+(?:\\.\\d{1,2})?\\s*(?:元|块|rmb|cny|usd|美元))"));
        entities.put("error_code", uniqueConcat(
                entities.get("error_code"),
                regexFind(message, "\\b[A-Z][A-Z0-9_-]{2,16}\\b")
        ));
        return entities;
    }
```

抽取方式是**正则**，不是模型输出：

| 实体         | 匹配规则                                  | 例子                      |
| ------------ | ----------------------------------------- | ------------------------- |
| `order_id`   | `订单号? / order / #` + 4–32 位字母数字   | “订单号 #12345” → `12345` |
| `date`       | 今天/明天/昨天/本周/下周，或 `2026-10-27` | “上周的订单” → `上周`     |
| `error_code` | 4xx/5xx 三位数字，或 3–16 位大写编码      | “一直 401” → `401`        |
| `amount`     | 带 ¥/元/块/rmb/usd 的数字                 | “多扣了 50 块” → `50 块`  |
| `product`    | 占位，**恒为空**                          | —                         |

每个实体都是 `List<String>`，可能抽出多个值。返回给前端长这样：

```json
"entities": { "order_id": ["12345"], "amount": ["50 块"], "error_code": [], "date": [], "product": [] }
```

**它有三个用处**：

1. **进提示词**：三个 Agent 的用户提示里都会拼一段 `[结构化实体]`（[BaseAgent.java:52-54](布丁智服/pudding-java/src/main/java/com/pudding/agent/BaseAgent.java#L52)），模型不用再从原句里猜订单号。
2. **参与路由打分**：错误码给技术 Agent +0.2，金额给账单 +0.15，订单号给通用 +0.1。
3. **可观测**：返回体里能直接看到“系统认为这句话里有哪些关键参数”，出问题好排查。

**两个已知粗糙点**（可以主动说）：`product` 是空占位；`error_code` 的大写编码规则会把 `API`、`JSON` 这类词误抓成错误码。

## 二、路由是不是「直接按意图」？

**不完全是。意图是主信号，但不是唯一信号。**

路由入口是 ，

```java
// src/main/java/com/pudding/agent/AgentOrchestrator.java
private RoutingDecision routeDecision(AgentRequest req) {
        if (req.urgency() == UrgencyLevel.CRITICAL) {
            return new RoutingDecision(AgentType.ESCALATION, List.of(), "紧急度为 CRITICAL，触发升级路由", 1.0);
        }
        if (req.intent() == IntentCategory.ESCALATION || req.intent() == IntentCategory.HUMAN_HANDOFF) {
            String intent = req.intent() == null ? "unknown" : req.intent().name().toLowerCase(Locale.ROOT);
            return new RoutingDecision(
                    AgentType.ESCALATION,
                    List.of(),
                    "意图为 " + intent + "，触发升级路由",
                    Math.max(req.intentConfidence(), 0.8)
            );
        }

        Map<AgentType, Double> scores = domainScores(req);
        Map<AgentType, Double> availableScores = new EnumMap<>(AgentType.class);
        scores.forEach((agentType, score) -> {
            if (agentType == AgentType.GENERAL || pool.containsKey(agentType)) {
                availableScores.put(agentType, score);
            }
        });
        if (availableScores.isEmpty()) {
            return new RoutingDecision(AgentType.GENERAL, List.of(), "无可用专属 Agent，降级到 GeneralAgent", 0.1);
        }

        List<Map.Entry<AgentType, Double>> ordered = availableScores.entrySet().stream()
                .sorted(Map.Entry.<AgentType, Double>comparingByValue().reversed())
                .toList();
        AgentType primary = ordered.getFirst().getKey();
        double primaryScore = ordered.getFirst().getValue();
        List<AgentType> supportingAgents = ordered.stream()
                .skip(1)
                .filter(entry -> entry.getKey() != AgentType.GENERAL)
                .filter(entry -> entry.getValue() >= 0.45 && entry.getValue() >= primaryScore * 0.55)
                .map(Map.Entry::getKey)
                .toList();
        return new RoutingDecision(
                primary,
                supportingAgents,
                routingReason(req, availableScores, primary, supportingAgents),
                round(Math.min(primaryScore, 1.0))
        );
    }

```

它按顺序做四件事：

**① 两条硬规则，直接绕过打分**

- 紧急度 `CRITICAL` → 直接走升级路由；
- 意图是 `ESCALATION` 或 `HUMAN_HANDOFF` → 直接走升级路由。

**② 低置信度澄清，也绕过路由**

`intent == OTHER` 且置信度 < 0.5 → 返回澄清话术，根本不算分。

**③ 三层信号加权打分**（）

```text
基础分：通用 0.1，技术 / 账单 0
意图加分：通用类意图 +0.55；技术三类 +0.75；账单六类 +0.75
关键词加分：每次命中 +0.18（技术/账单，封顶 0.45），通用 +0.12（封顶 0.35）
实体加分：error_code→技术 +0.2，amount→账单 +0.15，order_id→通用 +0.1
```

```java
// src/main/java/com/pudding/agent/AgentOrchestrator.java
private Map<AgentType, Double> domainScores(AgentRequest req) {
        String msg = req.message() == null ? "" : req.message().toLowerCase(Locale.ROOT);
        Map<AgentType, Double> scores = new EnumMap<>(AgentType.class);
        scores.put(AgentType.GENERAL, 0.1);
        scores.put(AgentType.TECHNICAL, 0.0);
        scores.put(AgentType.BILLING, 0.0);

        if (List.of(
                IntentCategory.QUERY,
                IntentCategory.ORDER_STATUS,
                IntentCategory.LOGISTICS,
                IntentCategory.REQUEST,
                IntentCategory.COMPLAINT,
                IntentCategory.GREETING,
                IntentCategory.FEEDBACK,
                IntentCategory.OTHER
        ).contains(req.intent())) {
            scores.merge(AgentType.GENERAL, 0.55, Double::sum);
        }

        if (List.of(
                IntentCategory.TECHNICAL,
                IntentCategory.TECHNICAL_LOGIN,
                IntentCategory.TECHNICAL_CRASH
        ).contains(req.intent())) {
            scores.merge(AgentType.TECHNICAL, 0.75, Double::sum);
        }

        if (List.of(
                IntentCategory.BILLING,
                IntentCategory.ACCOUNT,
                IntentCategory.ACCOUNT_SECURITY,
                IntentCategory.REFUND,
                IntentCategory.INVOICE,
                IntentCategory.PAYMENT_ISSUE
        ).contains(req.intent())) {
            scores.merge(AgentType.BILLING, 0.75, Double::sum);
        }

        long technicalHits = countHits(msg, "崩溃", "报错", "error", "crash", "无法登录", "登录失败", "500", "401", "验证码");
        long billingHits = countHits(msg, "退款", "退货", "扣款", "发票", "账单", "支付", "订阅", "refund", "invoice", "多扣");
        long generalHits = countHits(msg, "订单", "物流", "快递", "配送", "会员", "积分", "咨询", "帮助");

        scores.merge(AgentType.TECHNICAL, Math.min(0.45, technicalHits * 0.18), Double::sum);
        scores.merge(AgentType.BILLING, Math.min(0.45, billingHits * 0.18), Double::sum);
        scores.merge(AgentType.GENERAL, Math.min(0.35, generalHits * 0.12), Double::sum);

        Map<String, List<String>> entities = req.entities() == null ? Map.of() : req.entities();
        if (!entities.getOrDefault("error_code", List.of()).isEmpty()) {
            scores.merge(AgentType.TECHNICAL, 0.2, Double::sum);
        }
        if (!entities.getOrDefault("amount", List.of()).isEmpty()) {
            scores.merge(AgentType.BILLING, 0.15, Double::sum);
        }
        if (!entities.getOrDefault("order_id", List.of()).isEmpty()) {
            scores.merge(AgentType.GENERAL, 0.1, Double::sum);
        }

        scores.replaceAll((agentType, score) -> round(score));
        return scores;
    }

```



**④ 取最高分做主 Agent**；辅助 Agent 要同时满足 `≥0.45` 且 `≥ 主分×0.55` 才会并行。

### 为什么不能只说「按意图路由」

因为同一个意图下，关键词和实体会改变结果。举个真实例子：

```text
"登录一直 401，而且被扣了两次款"
意图：technical_login（技术 +0.75）
关键词：401 → 技术 +0.18；扣款 → 账单 +0.18
实体：401 → 技术 +0.2
最终：技术 1.13 做主，账单 0.18 不够辅助门槛 → 单 Agent 处理
```

再看一个：

```text
"我的订单 #12345 一直报错，还被多扣了 50 块"
意图：可能是 technical 或 billing（取决于三路投票）
关键词 + 实体：技术拿到 error_code +0.2，账单拿到 amount +0.15
结果：主辅可能同时成立 → 并行
```

所以准确说法是：**先判意图定大方向，再用关键词和实体修正，最后按分数选主辅**。

## 三、可以直接念（40 秒）

> 实体是从用户话里用正则抽出来的结构化参数：订单号、日期、错误码、金额。它有三个用处：拼进 Agent 的提示词，参与路由加分，以及返回给前端做可观测。
> 路由不是只看意图。意图决定基础加分，比如技术类意图直接给技术 Agent 加 0.75；但关键词每命中一次还会再加，实体也会加分，比如错误码给技术加 0.2、金额给账单加 0.15。最后取最高分做主 Agent，满足门槛的才并行。
> 另外有两条硬规则会绕过打分：紧急度 CRITICAL，或者意图本身就是转人工，直接走升级路由。
> 所以更准确的说法是：意图定方向，关键词和实体做修正，分数决定主辅。

这句话拆开是四个词：**复合问题、并行处理、路由原因、置信度**。逐一说。

## 一、什么算「复合问题」

一句话里同时包含两个领域的诉求，比如：

```text
"登录一直失败，退款和发票都不给处理，还多扣了 50 块"
```

它同时踩到技术（登录）、账单（退款/发票/扣款）两条线。单 Agent 只能答一半，所以要拆给多个 Agent。

## 二、系统怎么判断「该并行」

路由不是看意图一个信号，而是打分（[domainScores](布丁智服/pudding-java/src/main/java/com/pudding/agent/AgentOrchestrator.java#L213)）：

```text
基础分：通用 0.1
意图分：技术类意图 +0.75 / 账单类 +0.75 / 通用类 +0.55
关键词：每次命中 +0.18（技术/账单，封顶 0.45），通用 +0.12（封顶 0.35）
实体：错误码→技术 +0.2，金额→账单 +0.15，订单号→通用 +0.1
```

打分完，**主 Agent 取最高分**；**辅助 Agent 要同时满足两个条件**（[L199-203](布丁智服/pudding-java/src/main/java/com/pudding/agent/AgentOrchestrator.java#L199)）：

```text
分数 ≥ 0.45          绝对门槛：够格参与
分数 ≥ 主分 × 0.55   相对门槛：别把明显不如主力的拉进来
```

两个都满足才会并行。只设绝对门槛会把弱相关 Agent 全拉进来，延迟翻倍；只设相对门槛会出现两个都很低分一起并行。

## 三、一个具体例子

上面那句「登录失败，退款和发票都不给处理，还多扣了 50 块」：

| Agent | 算分                                                         | 结果           |
| ----- | ------------------------------------------------------------ | -------------- |
| 技术  | 意图 technical_login +0.75，关键词「登录失败」+0.18          | **0.93（主）** |
| 账单  | 关键词「退款/发票」+0.36、「多扣」+0.18（封顶 0.45），实体「50 块」+0.15 | **0.60（辅）** |
| 通用  | 基础分                                                       | 0.10           |

校验辅助门槛：`0.60 ≥ 0.45` ✅，`0.60 ≥ 0.93×0.55 = 0.51` ✅ → 并行。

## 四、「并行处理」具体怎么跑

```java
// runParallel
targets.stream().map(t -> CompletableFuture.supplyAsync(() -> execute(req, t)))  // 同时发起
futures.stream().map(CompletableFuture::join)                                    // 等最慢的那个
parts.add("[technical - 主处理]\n" + 内容)
parts.add("[billing - 辅助处理]\n" + 内容)
String.join("\n\n", parts)                                                       // 字符串拼接
```

要点：

- 总耗时 ≈ **最慢的那个 Agent**，不是两者相加；
- 合并是**结构化拼接**，不是再调一次 LLM 润色（省一次调用，代价是读起来像清单）；
- 某个 Agent 失败会退回通用再答一次；全部失败返回固定道歉；
- 线程池没指定，走的是 `ForkJoinPool.commonPool`，和全局异步任务共享。

## 五、「返回路由原因与置信度」是什么

API 返回体里的几个字段：

```json
{
  "intent": "technical_login",
  "primary_agent": "technical",
  "supporting_agents": ["billing"],
  "agent_types": ["technical", "billing"],
  "routing_reason": "intent=technical_login, group=technical, primary=technical, supporting=billing, scores=[technical=0.93, billing=0.60, general=0.10]",
  "routing_confidence": 0.93,
  "intent_confidence": 0.9
}
```

- **`routing_reason`**：把意图、分组、主辅 Agent、**每个 Agent 的分数**拼成一行字符串（[routingReason](布丁智服/pudding-java/src/main/java/com/pudding/agent/AgentOrchestrator.java#L275)）。
- **`routing_confidence`**：就是主 Agent 的得分，取了个 1.0 上限（[L209](布丁智服/pudding-java/src/main/java/com/pudding/agent/AgentOrchestrator.java#L209)）。

它的价值是**白盒可排查**：

```text
回答不好 → 看 routing_reason
  ├─ intent 本身就是错的 → 意图识别问题，去查三路投票
  └─ intent 对但 scores 不对 → 打分规则问题，去查关键词/实体权重
```

## 六、两个必须说准的点

1. **它不是概率**。`routing_confidence` 是人工规则算出来的分数，可能大于 1（被截断），也不能当「路由正确的概率」用。紧急升级路径的置信度是 `max(意图置信度, 0.8)`，转人工路径直接给 1.0。
2. **并行其实很少触发**。因为辅助要求「≥0.45 且 ≥ 主分×0.55」，而关键词单次只有 0.18、封顶 0.45，大多数单领域问题根本拉不出第二个合格 Agent。这是有意的保守设计，但也意味着「复合问题并行」在真实请求里属于少数路径。

## 七、面试版（40 秒）

> 复合问题是说一句话里有两个领域的诉求，比如登录失败加退款纠纷。
> 系统先按意图、关键词、实体给每个 Agent 打分，最高分做主 Agent；其他 Agent 要同时满足绝对门槛 0.45 和相对门槛「主分的 55%」才能做辅助，然后并行调用，总耗时取最慢的那个，结果按主处理和辅助处理拼起来。
> 返回里带 routing_reason 和 routing_confidence：前者把每个 Agent 的分数都列出来，后者是主 Agent 的得分。
> 这两个字段的价值是可排查：如果答案不好，能直接判断是意图判错了，还是意图对了但打分打错了。
