上下文与记忆：从 SKILL.md 热加载业务规范注入提示词，隔离越权话术并支持热更新；Redis 存会话工作记忆，JSON 与向量库存摘要和用户画像，向量操作走线程池避免阻塞主链路

Skills 是一条**「文件 → 扫描 → 匹配 → 拼进 system prompt」**的链路，热更新靠重新扫描，不靠重启。但它有一个部署上的坑，最后说。

热更新的本质一句话：**规范是「数据」不是「代码」，而注入点是每次请求时实时读取，所以换掉内存里的数据就行，不用重新编译、不用重启进程。**

## 一、先对比「重启」和「热更新」

假设你把账单规范里「不能承诺到账时间」改成「不能承诺具体日期」：

|          | 重启方式                               | 热更新方式          |
| -------- | -------------------------------------- | ------------------- |
| 操作     | 改文件 → 重新打包 → 重启容器/JVM       | 改文件 → 调一次接口 |
| 中断     | 重启期间请求失败                       | 不中断              |
| 内存状态 | 全部丢失（画像、Agent 统计、监控计数） | 全部保留            |
| 生效时间 | 几十秒到几分钟                         | 毫秒级              |
| 谁来做   | 开发/运维                              | 运营也能做          |

所以热更新的价值不是「技术上更酷」，而是**把业务规范的迭代和代码发版解耦**。

## 二、为什么能做到（三个代码事实）

**① 规范存在字段里，可以整体替换**

```java
// src/main/java/com/pudding/skill/SkillManager.java
private volatile List<Skill> skills = List.of();
```

`volatile` 保证：一个线程替换引用后，其他线程立刻能看到新值。

**② 重载是「构建新列表 + 换引用」，不是原地修改**

```java
// src/main/java/com/pudding/skill/SkillManager.java
public synchronized List<Skill> load() {
    List<Skill> loaded = new ArrayList<>();
    for (Path path : discoverFiles(root)) {
        Skill skill = loadFile(path);      // 全部读成新的对象
        if (skill != null) loaded.add(skill);
    }
    this.skills = List.copyOf(loaded);     // ← 最后一步才赋值
    this.errors = List.copyOf(loadErrors);
    return this.skills;
}

public List<Skill> reload() {
    return load();                          // 重载就是再跑一遍
}
```

关键点：

- `synchronized` 保证同时只有一个线程在重载；
- 引用赋值是原子的，所以**读的线程要么看到旧列表、要么看到新列表，不会看到「加载了一半」的列表**；
- 读路径（`promptFor`）不加锁，写少读多的场景性能最好。

**③ 注入发生在每次请求，不是启动时固化**

```java
// src/main/java/com/pudding/agent/BaseAgent.java
// BaseAgent.buildSystemPrompt()，每个请求都会走
String skillPrompt = skillManager.promptFor(request.message(), type().name().toLowerCase());
return systemPrompt() + "\n\n[动态 Skills]\n" + skillPrompt;
```

这里没有任何「prompt 缓存」。所以列表一换，**下一个请求**就自动用新规范。

## 三、时间线长什么样

```text
t0  你改 skills/billing_support/SKILL.md
      └─ 容器里 /app/skills 是挂载的，文件立刻就变了

t1  POST /skills/reload
      └─ load() 重新扫描 → 构建新 List → 替换 volatile 引用
      └─ 返回 {"count":3,"errors":[]}

t2  下一个 /chat 请求
      └─ promptFor() 读的是新列表 → 新规范进 system prompt

t1 之前已经在执行的请求
      └─ 它的 prompt 早就拼好了，继续用旧规范，不会中途改变
```

最后这条不是 bug，而是正确行为：**请求要么全程用旧规范，要么全程用新规范，不会一半旧一半新。**

## 四、热更新不覆盖什么（边界）

| 场景                                      | 能不能热更新 | 原因                                                 |
| ----------------------------------------- | ------------ | ---------------------------------------------------- |
| 改 SKILL.md 内容、关键词、agents、enabled | ✅            | 纯数据，reload 即可                                  |
| 加一个新的 skills 子目录                  | ✅            | 下一次 load 会扫描到                                 |
| 改 Skills 根目录路径                      | ❌            | 要改环境变量并重启                                   |
| 改 Java 代码（比如注入逻辑）              | ❌            | 要重新编译打包                                       |
| 加/改 Docker 挂载                         | ❌            | 要重建容器                                           |
| 多实例部署                                | ⚠️            | 调一次只 reload 当前实例，其他副本要各自调或滚动重启 |

还有三个工程上的短板（可以主动说）：

1. **没有文件监听**：不是「改了自动生效」，必须显式调 `/skills/reload`。想要自动，得加 WatchService 或定时扫描。
2. **没有版本和审计**：改坏了立即生效，只能手动改回去再 reload；`/skills` 只能看到当前内容长度，看不到历史。
3. **接口没有鉴权**：任何人能调 `/skills/reload`，虽然只是重读文件，但频繁调用会反复扫盘。生产上应该加 Token 或只允许内网。

## 五、你之前看到的现象正好能解释这个机制

之前 Docker 里 `count` 是 0：因为镜像没带 `skills/`，容器内 `/app/skills` 不存在，`load()` 直接返回空。

加上挂载后：

```text
GET  /skills          → count=3，path 显示 /app/skills/...
新增一个测试文件 → reload → count=4
删除该文件     → reload → count=3
```

`count` 能变，说明读的确实是**磁盘上的实时文件**，而不是启动时打进内存的副本——这就是「热」的证据。

## 六、面试版（30 秒）

> 热更新是把业务规范当数据而不是代码。Skills 加载后放在一个 volatile 列表里，reload 接口会重新扫目录、构建一个新列表、整体替换引用，读的线程要么看到旧的要么看到新的，不会看到中间状态。
> 注入点是每个请求实时调 promptFor，没有 prompt 缓存，所以下一个请求就用新规范，JVM 不用重启，画像和统计也不会丢。
> 它的边界是：只能热更规范内容，改代码、改挂载路径、加依赖还是要重启；多实例时每个实例都得各自 reload。

不是自动的。**没有文件监听、没有定时任务，必须有人或某个脚本主动调一次。**

## 现在的实际触发方式只有两种

| 方式           | 谁触发           | 代码                                                         |
| -------------- | ---------------- | ------------------------------------------------------------ |
| 前端按钮       | 人点「重新加载」 | `App.vue:265` → `backends.js:53` `POST /skills/reload` |
| curl / Swagger | 人手动调         | `curl -X POST http://localhost:8080/skills/reload`           |

```text
你改 SKILL.md
   │
   ├─ 什么都不做 ────────────► 文件变了，但内存里还是旧的，请求仍用旧规范
   │
   └─ 点「重新加载」或 curl ──► 后端 load() 重新扫盘 → 替换列表 → 下一个请求生效
```

## 几个容易混淆的点

1. **页面启动时只拉列表，不重载**：前端在初始化时会 `GET /skills` 显示已加载的 skill（`App.vue:453`），但 `POST` 只在你点按钮时发。
2. **接口本身没有鉴权**：任何能访问 8080 的客户端都能调，所以「谁都能发起」，但依然不是「系统自己发起」。
3. **改文件后不调接口，只有重启才生效**——因为启动时的 `@PostConstruct` 会再 load 一次。

## 如果你想要「自动热更新」

需要在后端加机制，三种常见做法：

```text
A. WatchService 监听 skills 目录变化 → 自动调 load()
   优点：实时；缺点：要处理编辑器「先删后建」的抖动，做防抖

B. 定时扫描（比如每 30 秒比对文件 mtime）→ 有变化才 load()
   优点：实现简单；缺点：最多延迟一个周期

C. 外部触发：CI / 运维脚本在发布规范后 curl 一次
   优点：可控、有审计；缺点：依赖发布流程
```

当前项目是 C 的手动版，连脚本都没接，纯人工。

## 面试版（20 秒）

> 不是自动的，得显式调 `POST /skills/reload`，要么人点前端的重新加载按钮，要么手动 curl。
> 因为后端没有文件监听，也没有定时扫描，改完文件不调接口是不生效的。
> 要做到自动，得加 WatchService 或者定时比对文件修改时间，再或者由发布脚本统一触发。

## 六、「隔离越权话术」是怎么做的

三层，**全是 prompt 层约束，没有硬拦截**：

| 层         | 做法                                                     | 效果                                          |
| ---------- | -------------------------------------------------------- | --------------------------------------------- |
| 角色隔离   | `agents: billing` 只在 BillingAgent 注入                 | 通用 Agent 看不到账单规范，不会跑去答退款时效 |
| 内容禁止项 | SKILL.md 里写「禁止承诺退款成功/禁止索要密码」           | 降低越权话术概率                              |
| 优先级声明 | 注入前缀写明「与系统角色冲突时以系统角色和安全边界为准」 | 规范不能覆盖角色定位                          |

**边界必须说清**：这三层都是「告诉模型别这么做」，不是「系统保证它不做」。`AnswerVerifier` 只看是否基于上下文、是否要转人工，**不检查话术合规**。真要硬隔离，得在生成后加规则校验或敏感话术拦截。

## 七、一个真实的部署缺口（重要）

我查了打包链路：

```text
Dockerfile:  COPY pom.xml / COPY src / COPY jar    ← 没有 COPY skills
compose:     只挂载 app-data:/app/data              ← 没有挂载 skills
```

应用的工作目录是 `/app`，而 Skills 的根目录配置是相对路径 `skills`，也就是 `/app/skills`——**这个目录在容器里不存在**。

结果：`load()` 里 `if (!Files.exists(root))` 直接返回空列表，`/skills` 的 `count` 会是 0。**也就是说，Docker 部署下「Skills 热加载」实际没有生效，只有本地 `mvnw spring-boot:run` 时才有。**

两种修法（任选）：

```dockerfile
# 方案 A：打进镜像
COPY skills ./skills
```

```yaml
# 方案 B：挂载，支持真正热更新
volumes:
  - ./skills:/app/skills:ro
```

改完 `docker compose up -d --build`（方案 A）或 `docker compose up -d`（方案 B），再 `curl http://localhost:8080/skills` 确认 count 从 0 变成 3。

## 一、Skills：加载 → 注入 → 热更新

**加载**（`core/skill_loader.py:92-116`）：`rglob` 先扫所有 `SKILL.md`，再补 `.md/.txt/.json`，跳过隐藏文件和 `README.md`；front matter 是**手写单行解析**（`_split_front_matter`，刻意不用 PyYAML），单文件失败只进 `errors`，不影响其他文件。

**注入**（`agents/agent_orchestrator.py:369-387`）：

```python
# agents/agent_orchestrator.py
def _build_system_prompt(self, req):
    base_prompt = (角色 + 职责 + 流程 + 输入契约 + 输出契约 + 升级条件 + 工具范围)
    if self._skill_manager is None:
        return base_prompt
    skill_prompt = self._skill_manager.prompt_for(req.message, self.agent_type.value)
    if not skill_prompt:
        return base_prompt
    return f"{base_prompt}\n\n[动态 Skills]\n{skill_prompt}"
```

所以 Python 的 system prompt 比 Java 厚一层：**角色契约 + 命中的 Skills**。ResponseComposer 也会给通用 Agent 注入一次（`L589-591`）。

**热更新**（`api/main.py:261-269`）：

```python
# api/main.py
@app.post("/skills/reload")
async def reload_skills():
    _skill_manager.reload()                    # 重新扫目录，替换 _skills
    _orchestrator.set_skill_manager(_skill_manager)  # 重新绑定到编排器
    return _skill_manager.summary()
```

`prompt_for` 每次请求都读 `self._skills`，所以下一个请求立刻生效；没有 prompt 缓存。

**越权隔离**同样是三层：`agents` 字段过滤角色、SKILL.md 里写禁止事项、注入前缀声明「与系统角色冲突时以系统角色和安全边界为准」。**仍然是提示词约束，不是硬拦截**。

**Docker 差异**：Python 镜像 `COPY . .` 带上了 `skills/`，compose 又挂了 `./skills:/app/skills`，所以容器里热更新是通的——这点比 Java 版好（Java 是我刚补的挂载）。

## 二、Redis 工作记忆

## 三、压缩：15 触发、留 5 条、摘要合并

`_compress()` 的步骤：

```python
# agents/memory_manager.py
to_compress = messages[:-5]
keep        = messages[-5:]
summary = LLM("用 2-3 句话总结…", max_tokens=256, temperature=0.0)

old_summary = await redis.get(skey) or ""
new_summary = await self._merge_summary(old_summary, summary)   # ★ 再调一次 LLM 合并
await redis.setex(skey, 86400, new_summary)

await self._store_episodic(...)     # 摘要存入 Chroma episodic
await redis.delete(key)             # 重置成最近 5 条
for m in reversed(keep):
    await redis.lpush(key, ...)
```

两个 Python 特有的点：

1. **摘要会合并**（`_merge_summary`，上限 800 字，失败回退成字符串拼接+截断），Java 版是直接追加；
2. 合并又是一次 LLM 调用，所以一次压缩最多 **2 次 LLM**，而且是在请求链路里 `await` 的——和 Java 一样会加到尾延迟。

## 四、向量库：Chroma 存情景记忆和画像

两个 collection：

```python
# agents/memory_manager.py
self._episodic = chroma.get_or_create_collection("episodic")      # 历史对话摘要
self._profile  = chroma.get_or_create_collection("user_profile")  # 用户画像
```

**情景记忆写入**（`_store_episodic`）：

```python
# agents/memory_manager.py
await asyncio.to_thread(
    self._episodic.add,
    ids=[md5(user+conv+time)],
    documents=[summary],                       # 只存摘要，向量由 Chroma 内置模型生成
    metadatas=[{"user_id":..., "conv_id":..., "ts":..., "full_text": text[:500]}],
)
```

**情景记忆检索**（`_search_episodic`）：

```python
# agents/memory_manager.py
results = await self._query_episodic(query, n_results=5,
            where={"user_id": uid, "conv_id": cid})
if len(docs) < 5:                              # 不足 5 条就放宽到只按用户过滤
    fallback = await self._query_episodic(query, 5, where={"user_id": uid})
return dedupe(docs)[:5]
```

**用户画像写入**（`update_profile`）：

```python
# agents/memory_manager.py
profile = LLM(最近 10 条消息 + 旧画像, max_tokens=512, temperature=0.0)
doc_id = f"user_profile:{user_id}"
await asyncio.to_thread(self._profile.delete, ids=[doc_id])   # 先删
await asyncio.to_thread(self._profile.add, ids=[doc_id], documents=[json.dumps(profile)],
                        metadatas=[{"user_id":..., "conv_id":..., "updated_at":...}])
```

注意：**画像是「按 id 取」，不是按相似度搜**（`_get_profile` 先 `get(ids=[doc_id])`，取不到才按 `where user_id` 查）。所以「用向量库存画像」严格说是**用向量库做持久化**，不是做语义检索。

## 五、「向量操作走线程池」到底在说什么

Chroma 的 Python 客户端是**同步 HTTP 调用**。如果在 `async def` 里直接调：

```python
# agents/memory_manager.py
self._episodic.query(...)   # 同步阻塞，整个事件循环卡住，所有并发请求一起停
```

所以全部包进 `asyncio.to_thread`：

| 位置       | 代码                                                         |
| ---------- | ------------------------------------------------------------ |
| 写情景记忆 | `await asyncio.to_thread(self._episodic.add, ...)`           |
| 查情景记忆 | `await asyncio.to_thread(self._episodic.query, ...)`         |
| 读写画像   | `await asyncio.to_thread(self._profile.get / delete / add, ...)` |

`asyncio.to_thread` 会把同步函数丢进默认线程池执行，事件循环继续处理其他请求。**这就是「避免阻塞主链路」的准确含义**。

顺带区分：

- Redis 用的是异步客户端，**不需要**线程池；
- LLM 调用本身是 async 的，也不需要；
- 只有 Chroma 这种同步客户端才需要 `to_thread`。

## 六、一次 `/chat` 的记忆链路

```text
main.py:287  mem_ctx = await _memory.get_context(user_id, conv_id, query=message)
              ├─ Redis  lrange wm:*        → 最近 20 条
              ├─ Chroma episodic.query     → top5（线程池）
              ├─ Chroma user_profile.get   → 画像（线程池）
              └─ Redis  get summary:*
             to_prompt_text() → [会话摘要] → [相关历史 3 条] → [用户画像] → [最近对话 8 条]

main.py:315  await add_message(USER)
main.py:316  await add_message(ASSISTANT)   → 可能触发 _compress（2 次 LLM，同步等待）
main.py:319  asyncio.create_task(update_profile(...))   ← 真正异步，不阻塞响应
```

注意 `to_prompt_text` 里最近对话只取 **`[-8:]`**，虽然 Redis 存了 20 条——Java 版是把 20 条全拼进去的。

## 七、Java vs Python 对照

| 维度          | Java                                       | Python                             |
| ------------- | ------------------------------------------ | ---------------------------------- |
| Redis 客户端  | `StringRedisTemplate`（同步）              | `redis.asyncio`（异步）            |
| 情景记忆      | 进程内 `CopyOnWriteArrayList` + 256 维哈希 | Chroma `episodic` + 内置 embedding |
| 画像          | `ConcurrentHashMap` + JSON 文件            | Chroma `user_profile`，按 id 取    |
| 摘要更新      | 追加                                       | LLM 合并（上限 800 字）            |
| 向量操作      | 内存计算，微秒级                           | 同步 HTTP → `asyncio.to_thread`    |
| 画像异步      | `@Async`                                   | `asyncio.create_task`              |
| 压缩          | 同步（在 addMessage 里）                   | 同步 `await`（在 add_message 里）  |
| 注入最近对话  | 20 条                                      | 8 条                               |
| Docker Skills | 原本没挂载（已补）                         | 镜像内 + 挂载，天然可用            |

## 八、已知问题（可以主动说）

1. **压缩在请求链路上**：一次压缩最多 2 次 LLM，会加尾延迟；可以改成 `create_task`，但要处理「压缩期间又有新消息」的竞态。
2. **画像异步导致本轮用旧画像**：新画像下一轮才生效。
3. **情景记忆无 TTL、无上限**：Chroma 会一直长。
4. **检索没有阈值**：`n_results=5` 一定返回 5 条，哪怕都不相关；注入时再取 3 条。
5. **`ensure_ascii=True`**：画像 JSON 里的中文会被转成 `\uXXXX`，token 变多，但能正常解析。
6. **`to_thread` 没有超时**：Chroma 卡住时，线程池会被占满（默认线程数有限），并发高了会成为新瓶颈。

## 九、面试版（60 秒）

> Python 版是三层记忆。工作记忆放 Redis，两个 key，一个 List 存最近 20 条，一个 String 存摘要，TTL 都是一天；到 15 条触发压缩，用模型总结并和旧摘要合并，然后只留最近 5 条。
> 情景记忆和用户画像放 ChromaDB 的两个 collection，摘要和历史片段存 episodic，跨会话按语义检索 top5；画像按 user_id 存成一条文档，每次对话后异步更新。
> 因为 Chroma 的 Python 客户端是同步 HTTP 调用，直接调会阻塞事件循环，所以所有向量操作都包在 `asyncio.to_thread` 里丢进线程池；Redis 用的是异步客户端，LLM 调用本身也是 async，都不需要线程池。画像更新用 `create_task`，不阻塞响应。
> 要说明的是，压缩是同步等待的，一次压缩最多两次模型调用，会加到尾延迟上；这是我下一步要改的。



你的质疑是对的：**用户画像确实不需要向量检索，代码里也确实没做向量检索**。向量只用在「情景记忆」上。分开说。

## 一、画像：按 id 取，不是向量搜

```python
# agents/memory_manager.py
async def _get_profile(self, user_id):
    doc_id = f"user_profile:{user_id}"
    direct = await asyncio.to_thread(self._profile.get, ids=[doc_id])   # ← 按 id 直接取
    if direct.get("documents"):
        return json.loads(direct["documents"][0])

    results = await asyncio.to_thread(self._profile.get, where={"user_id": user_id})  # 兜底按字段过滤
    return self._latest_profile_from_results(results)
```

两次都是**精确查找**（`ids` 或 metadata `where`），没有 `query_texts`、没有相似度。

所以「画像放在向量库里」这件事，本质是**把 Chroma 当持久化 KV 用**，不是当检索引擎。原因只有一个：项目已经依赖 Chroma 了，画像顺手放进去，少一套存储。代价是：

- Chroma 是同步客户端，所以还得 `to_thread` 包一层，反而多了开销；
- 一个用户只有一条文档，`delete + add` 覆盖，没有历史版本；
- 完全用不上它的向量能力。

Java 版就是更直接的做法：画像放 `ConcurrentHashMap` + JSON 文件。**如果要较真，Java 的处理更合理。**

## 二、向量检索只用在情景记忆上

```python
# agents/memory_manager.py
await self._episodic.add(
    ids=[md5(...)],
    documents=[summary],        # 每个片段是一条对话摘要
    metadatas=[{"user_id":..., "conv_id":..., "ts":..., "full_text": text[:500]}],
)

# 查询
results = await self._episodic.query(
    query_texts=[query], n_results=5,
    where={"user_id": uid, "conv_id": cid},
)
```

为什么这里必须用向量：

| 画像                   | 情景记忆                          |
| ---------------------- | --------------------------------- |
| 一个用户固定一条       | 一个用户 N 条历史片段，随时间累积 |
| 问题是「这个用户是谁」 | 问题是「哪几段历史跟这句话相关」  |
| key 能唯一定位         | **没有天然 key**，只能按语义找    |

用户问「上次那个退款的事怎么样了」，你要找的是「两周前那次对话里承诺过什么」。这句话和那条摘要在字面上可能完全不重合，**只有语义检索能找到**。

顺带说一个实现细节：检索是**先按 `conv_id` 过滤，取不满 5 条再放宽到只按 `user_id`**。所以平时只召回当前会话的历史，只有当前会话不够时才跨会话捞。

## 三、摘要（summary）有什么用

它解决的是「上下文装不下」和「跨轮承接」两个问题。

**作用一：替代被删掉的早期消息**

压缩时把前 N 条消息总结成两三句话，然后删掉原文只留最近 5 条：

```text
压缩前：20 条原文（约 3000 token）
压缩后：[摘要 150 字] + 最近 5 条（约 500 token）
```

如果不做这件事，只有两种结局：要么上下文爆炸（超窗口、成本飙升），要么截断丢掉早期承诺。

**作用二：承接跨轮指代**

```text
第 3 轮：用户说「我要退款，订单 #12345」
...
第 12 轮：用户说「那个还是没到账」
```

最近 5 条里已经没有订单号了，但摘要里还保留着「用户申请退款，订单 #12345，承诺 5-7 个工作日」，模型才能接上「那个」。

**作用三：给情景记忆提供「可检索的浓缩文本」**

压缩后的摘要会被写进 Chroma 的 `episodic`。因为摘要比原文短、信息密度高，向量检索时噪声更小；原文只截 500 字放在 metadata 里备查。

**作用四：控制成本**

摘要上限 800 字，且会和旧摘要合并（`_merge_summary`），不会无限增长。

## 四、为什么不能只靠画像或只靠原文

| 层                      | 回答的问题                                   | 为什么不能替代别人                         |
| ----------------------- | -------------------------------------------- | ------------------------------------------ |
| 工作记忆（Redis）       | 刚才聊了什么                                 | 只覆盖最近 20 条，更早的没了               |
| 摘要（Redis）           | 这个会话的来龙去脉                           | 是压缩后的线索，细节会丢                   |
| 情景记忆（Chroma）      | 哪几段历史跟当前问题相关                     | 是跨会话的片段库，不保证时序完整           |
| 用户画像（Chroma/JSON） | **这个用户是谁**（偏好、常用产品、问题类型） | 只有长期稳定信息，不含本次会话的待办和承诺 |

画像里不会写「用户正在等退款」，那是会话状态；摘要里不会写「这个用户偏好顺丰」，那是长期画像。**两者维度不同，不能互相替代。**

## 五、一个场景串起来

```text
用户（新会话）："上次那个退款到底什么时候到账？"

① 工作记忆：新会话，空的
② 摘要：新会话，空的
③ 情景记忆：用这句话去 episodic 里做向量检索
   → 命中两周前那条摘要「用户申请退款，订单 #12345，告知 5-7 个工作日」
④ 用户画像：按 user_id 直接取
   → {"preferences":["偏好在线客服"], "entities":{"问题类型":["退款"]}}
⑤ 拼成：摘要 + 相关历史(3条) + 画像 + 最近对话
```

没有第 ③ 步，模型不知道「上次那个」指什么；没有第 ④ 步，模型不知道这个人一贯关注什么。

## 六、面试版（40 秒）

> 用户画像是按 user_id 直接取的，没有用向量检索——代码里就是 `get(ids=[doc_id])`，放在 Chroma 里只是复用持久化，不是当检索引擎用。真正用向量的是情景记忆，因为一个用户有很多条历史片段，没有天然 key，只能按语义找「哪段历史和当前问题相关」。
> 摘要解决的是上下文装不下的问题：压缩时把早期消息总结成两三句话，替代被删掉的原文，既控制 token，又保留跨轮指代需要的关键信息，比如订单号和承诺过的时效。
> 三层分工是：工作记忆管刚才聊了什么，摘要管这个会话的来龙去脉，情景记忆管跨会话的相关片段，画像管这个用户是谁。四者维度不同，不能互相替代。



对，**物理上是四个存储，语义上是三层**。这个区别值得说清，因为面试官可能追问「到底几层」。

## 一、四者的实际位置

| #    | 名称     | 归属               | 存储（Python / Java）             | 生命周期            | 怎么取                          |
| ---- | -------- | ------------------ | --------------------------------- | ------------------- | ------------------------------- |
| 1    | 最近消息 | 工作记忆           | Redis List / Redis List           | TTL 24h，最多 20 条 | 按 `wm:{uid}:{cid}` 直接取      |
| 2    | 摘要     | 工作记忆的压缩产物 | Redis String（+ 副本进 episodic） | TTL 24h，≤800 字    | 按 `summary:{uid}:{cid}` 直接取 |
| 3    | 情景记忆 | 独立层             | Chroma `episodic` / 内存+JSON     | 持久                | 向量 top5 / 哈希余弦 top5       |
| 4    | 用户画像 | 独立层             | Chroma `user_profile` / Map+JSON  | 持久，按用户覆盖    | 按 `user_profile:{uid}` 直接取  |

## 二、为什么说「三层」而不是「四层」

因为 **1 和 2 属于同一层**：它们都是「当前这个会话」的短期状态，只是**原文 vs 压缩**两种形态。

```text
工作记忆（当前会话）
 ├─ 最近消息：原文，最多 20 条
 └─ 摘要：早期消息压缩后的 2-3 句话
```

拆成两个 key 是因为它们**读写模式不同**：消息要按条追加、按条截断；摘要要整段覆盖、要合并。放一个 key 里反而难操作。

所以准确说法是：

> **三层记忆（工作 / 情景 / 画像），四个存储位置**。

## 三、摘要为什么不算独立一层

判断标准是「解决什么问题」：

| 层       | 回答的问题                 |
| -------- | -------------------------- |
| 工作记忆 | 刚才聊了什么？             |
| 情景记忆 | 哪几段历史跟当前问题相关？ |
| 用户画像 | 这个用户是谁？             |

摘要回答的还是第一个问题，只是把「刚才」的窗口拉长了一点。它没有独立的检索方式（按 key 取），也没有独立的生命周期（和消息同一个 TTL），所以是工作记忆的一部分。

## 四、一个容易忽略的细节：摘要存在两处

压缩时摘要会写两次：

```python
# agents/memory_manager.py
await redis.setex(skey, 86400, new_summary)        # ① 当前会话的最新合并版
await self._store_episodic(user_id, conv_id, text, summary)  # ② 作为一条历史片段进 Chroma
```

- Redis 里：**当前会话**的摘要，会被不断合并覆盖，只有一份；
- Chroma 里：**历史片段**，每次压缩追加一条，可以有多条，能按语义检索。

所以「摘要」这个数据物理上出现了两次，但用途不同：一处给本轮拼接，一处给未来召回。

## 五、四者在 prompt 里的顺序

```text
[会话摘要]        ← 摘要
[相关历史]        ← 情景记忆 top5 里的前 3 条
[用户画像]        ← 画像 JSON
[最近对话]        ← 工作记忆
```

这个顺序也有讲究：越靠后越接近当前输入，模型注意力越高，所以最近对话放最后；摘要放最前，起「背景」作用。

## 六、面试怎么答

> 严谨说是三层记忆、四个存储。
> 三层是工作记忆、情景记忆、用户画像：工作记忆管当前会话，放 Redis；情景记忆管跨会话的相关片段，放向量库；画像管长期偏好，按 user_id 存。
> 四个存储是因为工作记忆内部又拆成两个 key：一个存最近 20 条原文，一个存压缩后的摘要。摘要本质是工作记忆的压缩产物，只是为了读写方便单独放了一个 key，不算独立一层。
> 另外摘要会同时写进 Redis 和情景记忆：前者给本轮拼接，后者给将来按语义召回。



Java 版的情景记忆检索就是一段「全量遍历 + 余弦排序」，没有索引、没有阈值。

## 二、检索本体

`MemoryManager.searchEpisodic`：

```java
// src/main/java/com/pudding/memory/MemoryManager.java
private List<String> searchEpisodic(String userId, String query) {
    if (query == null || query.isBlank()) {
        return List.of();                                  // 空消息直接返回，不算
    }
    double[] queryVec = embed(query);                      // ① 把当前问题向量化
    return episodicStore.stream()
            .filter(e -> e.userId().equals(userId))        // ② 只看这个用户的
            .sorted(Comparator.comparingDouble(
                    (EpisodicEntry e) -> cosine(queryVec, e.embedding())).reversed())  // ③ 按相似度降序
            .limit(5)                                      // ④ 取前 5
            .map(EpisodicEntry::summary)                   // ⑤ 只返回摘要文本
            .toList();
}
```

五步：**向量化 query → 按 userId 过滤 → 算余弦 → 排序取 5 → 返回摘要**。

注意三个细节：

1. **只按 userId 过滤，不按 conversationId**。所以它天然是「跨会话」的——你在 A 会话问的问题，可以召回 B 会话留下的摘要。这是设计意图。
2. **没有任何相似度阈值**。哪怕 5 条都只有 0.1 的相似度，也照样返回 5 条。
3. **没有时间衰减、没有去重、没有重要性权重**。三个月前的摘要和昨天的摘要，排序只看余弦值。

## 三、embed 具体怎么算

`MemoryManager.embed`：

```java
// src/main/java/com/pudding/memory/MemoryManager.java
double[] vector = new double[256];
String normalized = text == null ? "" : text.toLowerCase();
for (int n = 1; n <= 3; n++)
    for (int i = 0; i + n <= normalized.length(); i++) {
        String gram = normalized.substring(i, i + n);
        int hash = gram.hashCode();
        int idx = Math.floorMod(hash, 256);
        vector[idx] += (hash & 1) == 0 ? 1.0 : -1.0;
    }
```

- 1/2/3 字片段，映射到 256 个桶，用哈希最低位定符号；
- **没有剥标点**（这点和知识库的 tokenizer 不同），所以逗号、问号也会变成片段；
- 不存词频，同一片段出现多次会累加；
- 向量**不落盘**：`loadPersistentMemory()` 时用摘要原文重新算。

余弦（`MemoryManager.java:208`）就是标准点积除以模长，负值不截断（`cosine` 直接返回，可能为负）。

## 四、检索完还要再截一次

`searchEpisodic` 返回 5 条，但拼进 prompt 时只取 3 条（`MemoryContext.java`）：

```java
// src/main/java/com/pudding/memory/MemoryContext.java
if (relevantHistory != null && !relevantHistory.isEmpty()) {
    prompt.append("[相关历史]\n");
    relevantHistory.stream().limit(3).forEach(item -> prompt.append("- ").append(item).append('\n'));
}
```

所以「取 5 条、用 3 条」，留了 2 条的余量。

## 五、一个具体例子

假设 `episodicStore` 里有这些（都属于 u1001）：

| 摘要                                         | 和「退款到账了吗」的余弦 |
| -------------------------------------------- | ------------------------ |
| 用户申请退款，订单 #12345，告知 5-7 个工作日 | 0.62                     |
| 用户咨询发票抬头修改                         | 0.18                     |
| 用户抱怨物流慢，已补偿 5 元券                | 0.11                     |
| 用户改收货地址到北京朝阳                     | 0.05                     |
| 用户咨询会员积分规则                         | 0.02                     |
| （u1002 的）用户询问企业采购流程             | — 被 userId 过滤掉       |

排序后取前 5，去掉 u1002 那条，剩下 5 条全进 `relevantHistory`，最后 prompt 里呈现前 3 条。**哪怕后两条几乎不相关，也会进候选**——因为没有阈值。

## 六、Python 版的差异

```python
# agents/memory_manager.py
results = await asyncio.to_thread(
    self._episodic.query,
    query_texts=[query], n_results=5,
    where={"user_id": uid, "conv_id": cid},   # 先按会话过滤
)
if len(docs) < 5:
    fallback = await self._episodic.query(query_texts=[query], n_results=5,
                                         where={"user_id": uid})  # 不够再放宽到只按用户
```

|          | Java           | Python                                   |
| -------- | -------------- | ---------------------------------------- |
| 检索方式 | 全量遍历算余弦 | Chroma 内置 embedding + ANN              |
| 过滤条件 | 只按 userId    | 先 userId+convId，不足 5 再放宽到 userId |
| 返回     | 摘要文本       | 摘要文本（`documents`）                  |
| 阈值     | 无             | 无                                       |
| 注入     | 前 3 条        | 前 3 条                                  |

## 七、这套检索的短板（可以主动说）

1. **没有阈值**：永远返回 5 条，不相关也会塞进上下文，挤占 token 还可能误导模型。
2. **没有时间衰减**：老摘要和新摘要同权，但客服场景里「最近的」通常更重要。
3. **没有去重**：同一件事被压缩多次会产生多条相似摘要，可能占满 top5。
4. **Java 版是 O(N) 全表扫描**：条目多了每次请求都要遍历，应该换成向量库或加索引。
5. **粒度粗**：只在压缩时写入，一条摘要代表十几条消息，细节已经丢了，检索到也未必能回答细节问题。

## 八、面试版（40 秒）

> 情景记忆在每次请求开头检索，用当前用户这句话做 query。
> Java 版是先把 query 转成 256 维字符哈希向量，然后遍历所有情景记忆条目，只保留当前用户的，算余弦相似度降序，取前 5 条，最后注入 prompt 时再截前 3 条。
> 它只按 user_id 过滤，不按会话，所以是跨会话召回；但没有任何相似度阈值，也没有时间衰减，条目多了还是 O(N) 全表扫。
> Python 版换成 Chroma，先按会话过滤取 5 条，不够再放宽到只按用户，靠内置 embedding 做 ANN 检索，但没有阈值这个问题是一样的。



这个项目里「用线程」的地方一共三处，但**一个自定义线程池都没配**——全走默认池。先看现状，再说怎么正确用。

## 一、现状：三处并发 + 两个空配置类

| 位置          | 代码                                                         | 实际用的池                              |
| ------------- | ------------------------------------------------------------ | --------------------------------------- |
| 多 Agent 并行 | `AgentOrchestrator.java:123` `CompletableFuture.supplyAsync(...)` | **ForkJoinPool.commonPool**             |
| 检索 4 路并行 | `KnowledgeToolManager.java:49` `supplyAsync(...)` | **ForkJoinPool.commonPool**             |
| 画像异步更新  | `MemoryManager.java:72` `@Async` | Spring 默认 **applicationTaskExecutor** |
| 监控定时采集  | `@Scheduled(fixedDelay = 10000)`                             | **单线程**调度器                        |

而两个配置类是这样：

```java
// src/main/java/com/pudding/config/AsyncConfig.java
@Configuration
@EnableAsync
public class AsyncConfig { }          // 只有注解，零参数

@Configuration
@EnableScheduling
public class SchedulingConfig { }     // 同上
```

`@EnableAsync` 只是打开开关，没有定义任何 `Executor` Bean，所以 Spring Boot 用默认值。

## 二、默认池是什么、有什么问题

**① `supplyAsync` 不传 executor → commonPool**

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
CompletableFuture.supplyAsync(() -> search(subQuery, recallK))   // 没有第二个参数
```

- 并行度 = `CPU 核数 - 1`（比如 8 核就是 7 个线程）；
- 它是给**CPU 密集**的并行流设计的，和全局 `parallelStream()` 共用；
- 我们提交的任务是**阻塞 IO**（LLM 调用、HTTP），一个任务阻塞就占死一个 worker。

后果很直接：4 路子查询并发时，如果同时在处理多个 `/chat`，commonPool 很快被占满，**任务开始排队，延迟不可控**，还会影响其他用并行流的代码。

**② `@Async` → applicationTaskExecutor**

Spring Boot 默认：核心 8 线程、**队列无界**、最大线程数接近无限。无界队列意味着任务堆积时不会拒绝、不会扩容，只会一直排，最后 **OOM**。

**③ `future.get(30, SECONDS)` 是阻塞调用**

它阻塞的是 Tomcat 请求线程，而且超时后**不 cancel**，后台任务还在跑。线程被占着等，是另一种浪费。

**④ 没有隔离**

检索的线程池和编排共用 commonPool，检索一慢，编排也拿不到线程——一个环节的故障会传染。

## 三、正确用法：自定义两个池

```java
// src/main/java/com/pudding/config/AsyncConfig.java
@Configuration
@EnableAsync
public class AsyncConfig {

    /** 检索专用：IO 密集，允许稍多线程，队列有界 */
    @Bean("ragExecutor")
    public ThreadPoolTaskExecutor ragExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(16);
        ex.setQueueCapacity(200);
        ex.setKeepAliveSeconds(60);
        ex.setThreadNamePrefix("rag-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.initialize();
        return ex;
    }

    /** Agent 编排专用：任务少但耗时长，池子小而稳 */
    @Bean("agentExecutor")
    public ThreadPoolTaskExecutor agentExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(8);
        ex.setQueueCapacity(50);
        ex.setThreadNamePrefix("agent-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        ex.initialize();
        return ex;
    }
}
```

**改造调用点**：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
// 检索：显式传入池
CompletableFuture.supplyAsync(() -> search(subQuery, recallK), ragExecutor)

// 编排：显式传入池
CompletableFuture.supplyAsync(() -> execute(req, type), agentExecutor)

// 画像：指定池名
@Async("agentExecutor")
public void updateProfile(...)
```

**加超时和降级**（替代阻塞的 `get(30s)`）：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
future.orTimeout(30, TimeUnit.SECONDS)
      .exceptionally(ex -> fallbackResult(query));
```

`orTimeout` 会真正取消任务，不会让后台线程继续跑。

## 四、池参数怎么定（别拍脑袋）

```text
线程数 ≈ 并发请求数 × 每请求并行任务数 × (1 + 平均等待时间 / 平均计算时间)
```

- 检索是 IO 密集（等 LLM），等待占比高，池子可以比核数大；
- 编排也是等模型返回，同理；
- 但**队列必须有界**：无界队列等于把过载变成 OOM。

拒绝策略怎么选：

| 策略               | 行为           | 适用                               |
| ------------------ | -------------- | ---------------------------------- |
| `AbortPolicy`      | 直接抛异常     | 宁可失败也别拖，配合降级           |
| `CallerRunsPolicy` | 提交线程自己跑 | 保吞吐、自然限流，但会拖慢调用线程 |
| `DiscardPolicy`    | 静默丢弃       | 几乎不用，问题会被藏起来           |

## 五、Java 21 的另一种选择：虚拟线程

项目已经是 Java 21，对这种「大量阻塞 IO」的场景，虚拟线程比调线程池更省心：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

开了之后，`@Async` 和 Tomcat 请求处理都会用虚拟线程，阻塞成本极低，不需要精细调池大小。但要注意：**数据库连接池、HTTP 连接池仍然是有限资源**，虚拟线程解决的是线程不够，不是连接不够。

## 六、怎么观测线程池

```bash
curl http://localhost:8080/actuator/metrics/executor.active
curl http://localhost:8080/actuator/metrics/executor.queued
curl http://localhost:8080/actuator/metrics/executor.pool.size
```

没有这些指标，你永远不知道是「模型慢」还是「线程池排满了」。

## 七、面试版（40 秒）

> 这个项目里线程池用得比较粗糙：多 Agent 并行和检索并行都是 `supplyAsync` 不传 executor，走的是 ForkJoinPool 的 commonPool，并行度只有核数减一，而且任务是阻塞 IO，容易把 worker 占死；`@Async` 走 Spring 默认池，队列无界；`AsyncConfig` 里其实只有 `@EnableAsync`，一个参数都没配。
> 正确做法是定义两个有界队列的专用池，检索一个、编排一个，`supplyAsync` 显式传入，`@Async` 指定池名，再用 `orTimeout` 替代阻塞的 `get`，加上拒绝策略和指标。
> 另外项目是 Java 21，这种阻塞 IO 场景也可以直接开虚拟线程，比调池参数更省事。
