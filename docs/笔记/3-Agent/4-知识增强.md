知识增强：文档切片后走 BM25 + 向量混合召回、再用 LLM 重排，按意图触发检索减少无效检索和幻觉；检索工具加上查询改写、TTL 缓存与熔断兜底，单点失败不影响回复

这三个东西解决的是**三个不同问题**：改写管召回质量，缓存管重复成本，熔断管故障扩散。

## 一、为什么做查询改写

**问题**：用户的问法和文档的写法经常对不上，而且一句话只覆盖一个角度。

```text
用户："退款"
文档：退款政策里同时写了「7 天无理由」「1-3 个工作日审核」「5-7 个工作日到账」「已发货要先退货」
     —— 只用一个「退款」去检索，很容易只召回政策开头那一段
```

**做法**（`KnowledgeToolManager.rewriteQuery`）：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
String raw = llmGateway.chat("", prompt, 0.3, 256);   // 温度 0.3，需要一点多样性
List<String> rewritten = objectMapper.readValue(...);  // ["退款流程","退款时效","退款条件"]
List<String> queries = new ArrayList<>();
queries.add(query);                                    // 原始查询永远保留
rewritten.stream().filter(...).forEach(queries::add);
return queries.stream().distinct().toList();           // 最多 4 路
```

然后 4 路并行召回、按 chunk id 去重（`KnowledgeToolManager.java:48-55`），原始查询优先占位。

**为什么有效**：不是把 topK 调大（那会引入噪声），而是**用多个角度去撞同一批文档**，在不增加注入条数的前提下提高召回率。

**代价**：多一次 LLM 调用，几百毫秒；改写可能语义漂移，所以原始查询永远保留、失败就退化成单查询。

## 二、TTL 缓存是做什么的

**问题**：客服问题高度重复。「退款多久到账」一天可能被问几百次，而每次检索都要：LLM 改写 + 全库 BM25 扫描（这里还是 O(N²)）+ 向量计算 + LLM 重排。

**做法**（`KnowledgeToolManager.search()`）：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
String key = query + ":" + topK;
CacheEntry cached = cache.get(key);
if (cached != null && !cached.expired()) {
    return new ToolResult<>(true, cached.results(), "knowledge_search", null, true, 0, false);
}
...
cache.put(key, new CacheEntry(results, Instant.now().plusSeconds(300)));   // TTL 300 秒，懒过期
```

**为什么是 300 秒**：知识库变更频率低，但新增文档要能较快生效。TTL 就是「新鲜度 vs 成本」的折中：太长会答旧政策，太短等于没缓存。

**三个必须知道的坑**（都能在代码里验证）：

1. **新增知识不会主动失效缓存**：`/knowledge/add` 或 `/knowledge/upload` 之后，最多 5 分钟内搜不到新文档。正确做法是入库时按 key 前缀清缓存，或版本号入 key。
2. **缓存的粒度是单路子查询**，改写和重排不在缓存里——所以命中缓存省的是「BM25 + 向量扫描」，改写和重排每次照跑。想省这两次，得把缓存上移到 `searchWithRewrite` 层。
3. **实现很粗糙**：普通 `HashMap`（并发不安全）、没有容量上限、没有 LRU、没有命中率计数器；而且外层返回的 `cached` 标志恒为 `false`，**从返回值上看不出有没有命中缓存**。

## 三、熔断是做什么的

**问题**：检索依赖（LLM 改写/重排、知识库、线程池）如果持续故障，每个请求都要等到超时才返回——这里单路 30 秒、最坏 4 路 120 秒。线程被大量占住，一个依赖故障会拖垮整个应用。这叫**故障扩散**。

**做法**（`CircuitBreaker`）：

```text
CLOSED    放行请求
   │ 连续失败 ≥ 5 次
   ▼
OPEN      60 秒内直接拒绝，不再发请求，立即返回降级结果
   │ 60 秒后第一次请求
   ▼
HALF_OPEN 放行一次探测
   ├─ 成功 → 清零，回 CLOSED
   └─ 失败 → 立刻回 OPEN
```

**降级返回什么**（`KnowledgeToolManager.fallback`）：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
new SearchResult("fallback", "知识库降级结果",
    "知识库暂时不可用，未能完成对“xxx”的检索。请稍后重试，或转人工客服确认。",
    0.0, 0, Map.of("fallback", true, "error", error))
```

注意它 `success=true`：**这是有意的 fail-open**，让上层不用处理异常分支，照常生成回复。

**真实缺口**（面试主动说，别被问穿）：

- 内层 `search()` 把所有异常都吞成降级结果且 `success=true`，future 不抛异常，所以**实际只有 `future.get(30s)` 超时能累加失败计数**；
- `HALF_OPEN` 期间是全量放行，没有「只放一个探测」，并发下会惊群；
- `failCount` 在打开后不清零，下一次失败会很快再次打开。

## 四、「单点失败不影响回复」是怎么成立的

五层保险：

```text
1. 意图 gating：非业务意图根本不调检索        ← 少一个失败点
2. 熔断打开：直接返回 fallback，不等超时       ← 快速失败
3. 单路超时 30s：超时也返回 fallback           ← 有界等待
4. 任意异常 catch：统一转 fallback             ← 不向上抛
5. 上层拿到非空列表（fallback 一条），照常生成  ← 回复不中断
```

边界也要说清：

- fallback 的文本会**进到上下文里**，模型可能把「知识库暂时不可用」复述给用户；
- `success=true` 掩盖了故障，只能靠 `/monitor` 里的工具成功率和熔断状态发现；
- 超时后**不 cancel**，后台请求还在跑，极端情况下线程仍在被占用。

## 五、面试版（40 秒）

> 这三个是三个不同层面的保护。
> 查询改写是为了召回：用户一句话只覆盖一个角度，让模型生成三条不同角度的子查询加原始查询，四路并行召回再合并，这样能在不加大 topK 的情况下提高召回率，代价是多一次 LLM 调用。
> TTL 缓存是为了成本：客服问题重复率高，同一 query 加 topK 缓存 300 秒，命中就不再跑 BM25 和向量；缺点是新增知识不会主动失效，最多五分钟不可见。
> 熔断是为了可用性：连续失败 5 次就打开 60 秒，期间直接返回降级文本，不让每个请求都去等 30 秒超时。这三层加上异常兜底，保证检索挂了回复还能出来。

用一个生活场景讲，你马上就懂。

## 一、先想一个场景

你给一个同事打电话，没人接。

- **没有熔断的做法**：你每隔 10 秒拨一次，一直拨。电话占着你的时间，你什么也干不了；对方如果线路坏了，你还是一直拨。
- **有熔断的做法**：连拨 5 次都不通，你就停 1 分钟，这 1 分钟内**不再拨**，先干别的；1 分钟后试拨一次——通了就恢复正常，还不通就再停 1 分钟。

**熔断就是「连拨 5 次不通，先停 1 分钟」这个动作。**

## 二、它在程序里防的是什么

检索依赖（知识库、模型改写/重排）如果坏了，每个请求都会走到超时那一行：

```text
请求进来 → 调检索 → 等 30 秒 → 超时 → 返回
下一个请求 → 又等 30 秒 → 超时
...
```

问题不在于「这一次慢」，而在于**每个请求都在白等 30 秒**。线程是有限的，几十个请求同时白等，线程池就满了，**连不依赖检索的功能也被拖死**。一个组件的故障，传染成整个系统的故障，这叫**雪崩**。

熔断做的事只有两件：

1. **快速失败**：别等了，直接返回一个兜底结果（0 毫秒）；
2. **定期试探**：过一段时间放一个请求去试，好了就恢复，没好就继续拦。

## 三、三个状态 + 一条时间线

```text
       连续失败 ≥ 5 次
CLOSED ────────────────► OPEN
（正常放行）              （60 秒内全部直接拒绝）
   ▲                        │
   │ 试探成功                │ 60 秒后
   │                        ▼
   └──────────────────── HALF_OPEN
       试探失败 → 回到 OPEN     （放请求去试）
```

用请求序列看更直观：

```text
没熔断：
请求 1  → 等 30s → 超时
请求 2  → 等 30s → 超时
请求 3  → 等 30s → 超时
... 100 个请求，累计等了 3000 秒，线程全被占住

有熔断（5 次 / 60 秒）：
请求 1~5   → 失败，计数 1 2 3 4 5 → 状态变 OPEN
请求 6~100 → 立刻返回「知识库暂时不可用」（不等，不占线程）
60 秒后    → 放请求 101 去试探
              ├─ 成功 → 恢复正常，继续服务
              └─ 失败 → 继续 OPEN，再等 60 秒
```

    state = CLOSED;      // 试探成功，恢复正常

    if (failCount >= threshold) {   // 5 次

被拒绝时返回的兜底长这样：

```text

 请稍后重试，或转人工客服确认。"
```

注意它 `success = true`：**故意不抛异常**，让上层照常生成回复。这就是「单点失败不影响回复」的意思——检索没了，回复还能出来，只是内容质量下降。

## 五、别和另外两个概念混

| 概念 | 做什么               | 类比                     |
| ---- | -------------------- | ------------------------ |
| 重试 | 失败了**再试一次**   | 电话没接，再拨一遍       |
| 限流 | **少放一些**请求进来 | 门口限流，一次进 10 个人 |
| 熔断 | **暂时完全不试**     | 连拨 5 次不通，停 1 分钟 |

熔断的作用不是修复故障，而是**止损**：让故障只在它自己那一层，不扩散到整个系统。

## 六、这个项目里的真实缺口（面试可以主动说）

1. **只有超时能真正触发熔断**：内层 `search()` 把异常都吞成了兜底结果且 `success=true`，异常不会往上抛，所以失败计数基本只在 `future.get(30s)` 超时时才增加。
2. **半开状态是全量放行的**，没有「只放一个探测请求」，并发高的时候会一起冲进去，叫惊群。
3. **失败计数打开后不清零**，恢复后很快又会被打回打开状态。

## 七、可以直接念（30 秒）

> 熔断就是「连续失败几次之后，先别再试了」。
> 因为检索依赖一旦变慢或挂掉，每个请求都会卡在超时上，线程被白等占满，最后整个服务都被拖垮。
> 所以设置了连续失败 5 次就打开 60 秒，这 60 秒内不再发请求，直接返回一句「知识库暂时不可用，请稍后重试或转人工」；60 秒后放一个请求去试探，成功就恢复正常，失败就继续拦着。
> 它不修复故障，只负责止损，保证检索挂了，回复还能出来。

## ③ BM25

`KnowledgeBaseService.bm25Scores`：

```java
// src/main/java/com/pudding/knowledge/KnowledgeBaseService.java
double avgDl = documents.stream().mapToInt(d -> tokenize(d.content()).size()).average().orElse(1.0);
double k1 = 1.5;
double b = 0.75;
for (KnowledgeDocument doc : documents) {
    List<String> terms = tokenize(doc.content());
    double score = 0.0;
    for (String term : queryTerms) {
        long tf = terms.stream().filter(term::equals).count();
        if (tf == 0) continue;
        long df = documents.stream().filter(d -> tokenize(d.content()).contains(term)).count();
        double idf = Math.log(1 + (documents.size() - df + 0.5) / (df + 0.5));
        double denom = tf + k1 * (1 - b + b * terms.size() / avgDl);
        score += idf * (tf * (k1 + 1)) / denom;
    }
    scores.put(doc.id(), score);
}
return normalize(scores);   // 除以本轮最大值
```

分词器（L238-255）：小写 → 剥 ASCII 标点 → 空格切词 → **再补 2-gram、3-gram**。因为中文没有空格，只靠空白切会得到整句一个 token。

## ④ 向量（256 维特征哈希）

for (String gram : grams) {

## ⑦ 外层工具治理（简历里的「查询改写、TTL 缓存与熔断」）

`KnowledgeToolManager.searchWithRewrite`：

```java
// src/main/java/com/pudding/tool/KnowledgeToolManager.java
if (!breaker.allow()) return fallback(...);               // 熔断 5 次 / 恢复 60s
List<String> queries = rewriteQuery(query);               // 1 原始 + 3 子查询（temp 0.3）
int recallK = Math.max(topK, 5);
List<CompletableFuture<...>> futures = queries.stream()
        .map(q -> CompletableFuture.supplyAsync(() -> search(q, recallK)))  // 4 路并行
        .toList();
for (var future : futures) {
    for (SearchResult r : future.get(30, TimeUnit.SECONDS).data()) {        // 每路 30s 超时
        merged.putIfAbsent(r.id(), r);                    // 按 chunk id 去重，原始查询优先
    }
}
List<SearchResult> reranked = rerank(query, new ArrayList<>(merged.values()), topK);
```

外加：`search()` 里 `cache.put(key, new CacheEntry(results, now + 300s))`，key 是 `query:topK`，TTL 300 秒，普通 `HashMap`。

## 这条链路对「减少幻觉」到底起了什么作用

| 机制               | 作用                                | 边界                                         |
| ------------------ | ----------------------------------- | -------------------------------------------- |
| 意图 gating        | 闲聊/转人工不检索，避免噪声入上下文 | 只看意图，判成 OTHER 就跳过                  |
| 切片 500/80        | 检索粒度合理，条款不被切断          | 重排只看前 180 字，长块尾部看不到            |
| BM25 + 向量融合    | 关键词与近形表达互补                | 向量是哈希投影，语义增量有限                 |
| LLM 重排           | 把「相似」修成「相关」              | 候选 ≤ topK 不调；失败回退融合分             |
| **没有相似度阈值** | ——                                  | 只要检索成功就必返 top-3，知识库没有也会硬塞 |

所以准确说法是：**这条链路降低了「检索不到」和「检索噪声」的概率，但没有消除幻觉**——真正的兜底需要阈值 + 无命中拒答 + 校验拦截，这三样目前都缺。

## 面试版（50 秒）

> 触发在 Controller：先做意图识别，只有 14 类业务意图才调检索，另外 5 类直接跳过，这样闲聊和转人工不会把噪声塞进上下文。
> 检索内部先在工具层做查询改写，生成三条子查询加原始查询，四路并行召回，每路取 5 条，按 chunk id 去重。
> 每一路召回走的是混合检索：BM25 用 k1 1.5、b 0.75，向量是 256 维符号特征哈希，两路各自按最大值归一后 0.45 和 0.55 加权融合，取 topK。
> 合并后如果候选数大于 topK，再用一次低温度 LLM 重排，每条只给它看 180 字，失败就回退到融合分排序。
> 最后取 top3 拼成知识上下文。要说明的是，这条链路没有相似度阈值，所以它减少的是无效检索和噪声，不是彻底消除幻觉。
