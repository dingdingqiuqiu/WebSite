监控与评测：Prometheus 采集 Agent 成功率与延迟并回写路由做动态降权，评测覆盖意图 Accuracy 和 LLM-as-Judge 四维打分，支持 baseline 回归检测



「降权」这个词可以拆成两个字：**权重**是被选中的倾向，**降权就是把这个倾向调低**。放到这个项目里，就是**给表现变差的 Agent 扣分，让路由层少选它**。

## 一、先看它想解决什么问题

三个 Agent 里，技术 Agent 正常情况下最合适接技术问题。但如果它最近成功率掉了、延迟涨了，语义上它仍然「最匹配」，可实际上它已经不适合接单了。

监控的作用就是：**别只看「谁该接」，还要看「谁现在接得住」。**

类比：主管排班。某个员工这周状态差、出错多，不会开除他，但会**少给他排班**——这就是降权。

## 二、代码里是三层数值

```text
原始指标           success_rate、avg_ms          ← 事实
    ↓
惩罚分 penalty      0 ~ 0.9                      ← 规则算出来的"扣分"
    ↓
路由分 routingScore base × (1 − penalty)          ← 实际参与比较的分数
```

### 第一层：原始指标

```java
// src/main/java/com/pudding/agent/AgentStats.java
AgentStats.record(ok, latencyMs)   // 每次 Agent 调用后记一笔
successRate() = success / total
avgLatencyMs() = totalLatency / total
```

### 第二层：惩罚分

```java
// src/main/java/com/pudding/monitor/PerformanceMonitor.java
private double routingPenalty(double successRate, double avgMs) {
    double penalty = 0.0;
    if (successRate < 0.90) penalty += Math.min(0.5, (0.90 - successRate) * 2);
    if (avgMs > 3000)       penalty += Math.min(0.4, (avgMs - 3000) / 10000);
    return Math.min(0.9, penalty);
}
```

两个扣分项，各自封顶：

| 指标     | 阈值   | 扣分规则           | 上限 |
| -------- | ------ | ------------------ | ---- |
| 成功率   | 0.90   | 每低 0.01 扣 0.02  | 0.5  |
| 平均延迟 | 3000ms | 每超 1000ms 扣 0.1 | 0.4  |
| 合计     | —      | —                  | 0.9  |

**最多扣到 0.9**，也就是路由分最低保留 10%——不会直接清零，因为「完全不用」应该由熔断/升级去做，降权只做「少用」。

### 第三层：路由分

```java
// src/main/java/com/pudding/agent/AgentStats.java
double latencyScore = 1.0 / (1.0 + avgLatencyMs() / 1000.0);
double base = successRate() * 0.7 + latencyScore * 0.3;
return base * Math.max(0.0, 1.0 - monitorPenalty);
```

注意这里是**乘法**，不是减法：`base × (1 − penalty)`。惩罚越重，压得越狠。

## 三、算一个具体例子

|                  |   健康时 |             变差时 |
| ---------------- | -------: | -----------------: |
| 成功率           |     1.00 |               0.80 |
| 平均延迟         |    500ms |             5000ms |
| latencyScore     |    0.667 |              0.167 |
| base             |     0.90 |               0.61 |
| penalty          |        0 | 0.20 + 0.20 = 0.40 |
| **routingScore** | **0.90** |          **0.366** |

分数从 0.90 掉到 0.366，**降了 59%**。这就是「降权」的实际效果：不是禁用，是让它很难被选中。

## 四、降权「本来」要影响什么

设计意图是两层：

```text
① 同类型多实例之间择优
   technical-0 成功率 0.95 → score 0.88
   technical-1 成功率 0.70 → score 0.42
   → 路由优先选 technical-0

② 跨 Agent 类型的选择
   technical 惩罚后 0.68，billing 0.75
   → 主 Agent 从 technical 换成 billing
```

## 五、为什么现实中没生效（重点）

代码只做到了第 ① 层：

```java
// src/main/java/com/pudding/agent/AgentOrchestrator.java
private Optional<BaseAgent> bestAgent(AgentType type) {
    return pool.get(type).stream()
            .max(Comparator.comparingDouble(a -> a.stats().routingScore()));  // 只在同类实例里比
}
```

而 `AgentConfig` 里每类**只有一个实例**：

```java
// src/main/java/com/pudding/config/AgentConfig.java
AgentType.GENERAL,   List.of(new GeneralAgent(...)),
AgentType.TECHNICAL, List.of(new TechnicalAgent(...)),
AgentType.BILLING,   List.of(new BillingAgent(...))
```

一个实例自己跟自己比，`routingScore` 再低也还是它。第 ② 层（跨类型）用的是 `domainScores()`，那里**根本没有 penalty 这一项**。

所以现在的真实状态是：

> **penalty 能算、能写回、能看，但改变不了路由结果，只起到告警作用。**

## 六、怎么让它真正生效

**改法一：乘进领域分（最小改动）**

```java
// src/main/java/com/pudding/agent/AgentOrchestrator.java
Map<AgentType, Double> scores = domainScores(req);
scores.replaceAll((type, s) -> s * (1 - penaltyOf(type)));
// 再取最高分
```

效果：技术 Agent 惩罚 0.4 时，1.13 × 0.6 = 0.68，可能被账单 Agent 的 0.75 反超，主 Agent 就真的换了。

**改法二：同类型多实例 + 按 routingScore 选**

这类要配合部署两个 technical 实例（可以是不同模型），让 ① 层有比较对象。

**两个都要做一点**：只做 ① 需要多实例成本；只做 ② 会让单实例的 Agent 永远被压，容易误伤。

## 七、别和这几个概念混

| 概念         | 做什么           | 力度           |
| ------------ | ---------------- | -------------- |
| 降权 penalty | 降低被选中的倾向 | 软，仍可能被选 |
| 熔断         | 暂时完全不调用   | 硬，直接拒绝   |
| 限流         | 少放请求进来     | 入口层         |
| 告警         | 通知人来看       | 不改变行为     |
| 重试         | 失败了再试       | 增加负担       |

降权是**最软的一档**：它假设「这个 Agent 只是状态不好，不是坏了」，所以给个惩罚分让它退居二线，而不是直接停用。

## 八、面试版（40 秒）

> 降权就是给表现变差的 Agent 扣分，让路由少选它。
> 具体是每 10 秒汇总一次成功率和平均延迟，成功率低于 0.9 开始扣，每低 0.01 扣 0.02，最多扣 0.5；平均延迟超过 3000 毫秒，每超 1000 扣 0.1，最多扣 0.4；总惩罚封顶 0.9。
> 然后路由分等于成功率乘 0.7 加延迟分乘 0.3，再乘 1 减惩罚。比如成功率从 1.0 掉到 0.8、延迟从 500 涨到 5000，路由分会从 0.9 掉到 0.37。
> 但要说明，这个降权现在只在同类型多实例之间择优时生效，而项目里每类只有一个实例，所以它实际只起告警作用。要真正闭环，得把惩罚乘进领域打分，让跨 Agent 的选择也受影响。





这问题问到点子上了。**成功率的口径很宽，而「表现差」的判定是一刀切的阈值规则**——两处都不够严谨。

## 一、成功率怎么算

### 数据结构

```java
// src/main/java/com/pudding/agent/AgentStats.java
// AgentStats
AtomicLong total, success, totalLatencyMs;

public void record(boolean ok, long latencyMs) {
    total.incrementAndGet();
    if (ok) success.incrementAndGet();
    totalLatencyMs.addAndGet(latencyMs);
}

public double successRate() {
    return total.get() == 0 ? 1.0 : (double) success.get() / total.get();
}
```

就是 **成功次数 / 总次数**，没有时间窗口、没有衰减、没有分类。

### `ok` 是怎么判定的

全部来自 `BaseAgent.handle()`：

```java
// src/main/java/com/pudding/agent/BaseAgent.java
public AgentResponse handle(AgentRequest request) {
    try {
        String content = llmGateway.chat(...);
        stats.record(true, latency);        // ← 只要没抛异常，就是成功
        return new AgentResponse(...);
    } catch (Exception ex) {
        stats.record(false, latency);       // ← 只有抛异常，才是失败
        return new AgentResponse(type(), "抱歉，处理您的请求时出现问题…", false, ...);
    }
}
```

**所以「成功」= LLM 调用没有抛异常。**

它不代表回答好。下面这些都算「成功」：

| 情况                       | 算成功吗 |
| -------------------------- | -------- |
| 模型返回空字符串           | ✅ 成功   |
| 模型返回「抱歉我无法处理」 | ✅ 成功   |
| 答非所问                   | ✅ 成功   |
| 触发了转人工/升级          | ✅ 成功   |
| 超过 30 秒但没超时         | ✅ 成功   |
| 网络异常 / 解析异常        | ❌ 失败   |

还有两个**不计入 Agent 成功率**的失败：

- `AnswerVerifier` 校验不通过 —— 它在 Agent 外面，不参与统计；
- 检索失败 —— 被工具层吞成 `fallback + success=true`，只进工具统计。

### 冷启动的极端情况

```text
total = 0  → successRate() 返回 1.0      ← 乐观初始，新实例不被惩罚
total = 1，失败 1 次 → 0.0              ← 一次失败直接掉到 0%
```

所以一个低频 Agent，**第一次调用失败就会被判成 0% 成功率**，penalty 直接吃满 0.5。

## 二、「表现差」怎么判定

### 规则

每 10 秒读一次累计值，两条硬阈值（`PuddingProperties` 里默认）：

```text
success_rate < 0.90   → 告警 + 扣分
avg_ms       > 3000   → 告警 + 扣分
```

扣分公式：

```java
// src/main/java/com/pudding/monitor/PerformanceMonitor.java
penalty = min(0.5, (0.90 - sr) * 2) + min(0.4, (avg - 3000) / 10000)
penalty = min(0.9, penalty)
```

### 举个例子

```text
某 Agent 最近 10 次调用：成功 9 次，平均 3200ms
sr = 0.9         → 不扣分（等于阈值，不触发）
avg = 3200       → 扣 (3200-3000)/10000 = 0.02
penalty = 0.02   → 几乎无感

另一次：成功 7 次 / 10 次，平均 8000ms
sr = 0.7         → 扣 (0.9-0.7)*2 = 0.4（封顶 0.5）
avg = 8000       → 扣 (8000-3000)/10000 = 0.5 → 封顶 0.4
penalty = 0.8
```

然后 `routingScore = base × (1 − 0.8)`，被压到原来的 20%。

### 这是「规则判定」，不是「统计判定」

它没有：
- 置信区间 / 显著性检验；
- 滑动窗口；
- 基线对比；
- 最小样本量。

就是「低于阈值就扣分」。

## 三、这套判定哪里不严谨（可以说得很具体）

| 问题                   | 后果                                                         |
| ---------------------- | ------------------------------------------------------------ |
| **成功率 ≠ 质量**      | 只要不抛异常就算成功，答得烂的 Agent 成功率仍是 100%         |
| **没有最小样本量**     | 1 次失败 → 0%，被误杀；反之 1 次成功 → 100%，被高估          |
| **累计计数不衰减**     | 早上一次故障会永久拉低成功率，恢复后要跑很久才回升           |
| **用平均值不用分位数** | 一条 30 秒超时能把均值拉高；p95 才能反映长尾体验             |
| **阈值一刀切**         | 技术排障天然比问候慢，3000ms 对它是苛刻的                    |
| **双重惩罚**           | `routingScore` 已经乘了成功率、已经算了延迟分，再乘 `1−penalty`，等于同一个信号扣两次 |
| **只看 Agent 层**      | 检索失败、校验失败都不进这个成功率                           |
| **没有同类对比**       | 无法区分「绝对表现差」和「相对别人差」                       |
| **没有业务指标**       | 转人工率、重复提问率、用户反馈都不在统计里                   |

## 四、要判断「真的表现差」，应该怎么做

### ① 把成功重新定义

```java
// src/main/java/com/pudding/agent/BaseAgent.java
boolean ok = verification.pass()
          && verification.grounded()
          && !escalated
          && !content.isBlank()
          && !content.contains("抱歉");
```

也就是从「没抛异常」升级成「质量通过」。

### ② 用滑动窗口 + 最小样本

```text
只看最近 N=100 次（或最近 5 分钟）
样本数 < 20 时不计算 penalty（避免冷启动误判）
```

### ③ 用分位数而不是平均值

```text
p95 延迟 > 5000ms 才算慢，平均值受极端值影响太大
```

### ④ 分 Agent 设阈值

```text
general   : sr ≥ 0.95, p95 ≤ 1500ms
technical : sr ≥ 0.90, p95 ≤ 5000ms
billing   : sr ≥ 0.95, p95 ≤ 3000ms
```

### ⑤ 惩罚项去重

要么 `routingScore` 里不再重复计成功率和延迟，只乘 penalty；要么 penalty 只反映「额外信号」（比如连续失败次数、错误率突增），不要和 base 重复。

### ⑥ 加恢复机制

```text
连续 3 个采集周期表现正常 → penalty 逐步衰减到 0
而不是一直保留历史最差值
```

### ⑦ 加业务指标

```text
转人工率、二次追问率、用户点踩率、平均对话轮数
这些才是「客服好不好」的直接信号
```

## 五、面试版（40 秒）

> 成功率就是成功次数除以总次数，但「成功」的定义很宽：只有 LLM 调用抛异常才算失败，返回空、答非所问、甚至转人工都算成功。校验不通过也不进这个统计。
> 判定表现差是两条硬阈值：成功率低于 0.9、平均延迟高于 3000 毫秒，按公式扣一个 0 到 0.9 的惩罚分。它没有滑动窗口、没有最小样本量，也没有显著性检验，所以一个低频 Agent 失败一次就会被判成 0% 成功率。
> 要更准，得把成功重新定义成「校验通过且没有升级」，用滑动窗口和 p95 延迟，加最小样本门槛，并且把惩罚项和路由分里已有的成功率去重，否则是同一个信号扣两次。



这条 bullet 是**两个闭环**：监控闭环（运行时 → 路由）和评测闭环（离线 → 回归）。分开讲，最后说它们各自的断点。

## 一、监控：采集 → 算分 → 写回 → 暴露

### 1. 数据从哪来

每次 Agent 调用结束，`BaseAgent.handle()` 会记一笔：

```java
// src/main/java/com/pudding/agent/BaseAgent.java
boolean escalate = needsEscalation(content);
stats.record(true, latency);     // 成功 + 耗时
// 异常分支
stats.record(false, latency);    // 失败 + 耗时
```

`AgentStats` 里就是三个原子计数：

```java
// src/main/java/com/pudding/agent/AgentStats.java
total.incrementAndGet();
if (ok) success.incrementAndGet();
totalLatencyMs.addAndGet(latencyMs);
```

成功率 = `success / total`，平均延迟 = `totalLatencyMs / total`。

### 2. 每 10 秒汇总一次

`PerformanceMonitor.collect()`：

```java
// src/main/java/com/pudding/monitor/PerformanceMonitor.java
@Scheduled(fixedDelay = 10000)
public void collect() {
    monitorCollectionTimer.record(() -> {
        monitorCollections.increment();
        Map<String, Object> agentStats = orchestrator.stats();   // general_0 / technical_0 / billing_0
        agentStats.forEach((key, value) -> {
            double sr  = success_rate;
            double avg = avg_ms;
            if (sr  < 0.90) addAlert("agent_success_rate:" + key, sr, 0.90);
            if (avg > 3000) addAlert("agent_avg_ms:" + key, avg, 3000);
            penalties.put(key, routingPenalty(sr, avg));         // 算降权
        });
        orchestrator.updateRoutingPenalties(penalties);          // 写回
    });
}
```

### 3. 降权公式

```java
// src/main/java/com/pudding/monitor/PerformanceMonitor.java
private double routingPenalty(double successRate, double avgMs) {
    double penalty = 0.0;
    if (successRate < 0.90) penalty += Math.min(0.5, (0.90 - successRate) * 2);
    if (avgMs > 3000)       penalty += Math.min(0.4, (avgMs - 3000) / 10000);
    return Math.min(0.9, penalty);
}
```

举例：成功率 0.80、平均延迟 5000ms

```text
成功率项：(0.90 − 0.80) × 2 = 0.20
延迟项：  (5000 − 3000) / 10000 = 0.20
合计：    0.40
```

### 4. 写回后影响什么

`setMonitorPenalty()` 把值存进 AgentStats（限幅 0~0.9），然后影响 `routingScore()`：

```java
// src/main/java/com/pudding/agent/AgentStats.java
double latencyScore = 1.0 / (1.0 + avgLatencyMs() / 1000.0);   // 延迟越低越接近 1
double base = successRate() * 0.7 + latencyScore * 0.3;
return base * Math.max(0.0, 1.0 - monitorPenalty);             // 惩罚是乘法
```

这个分数只在一处被用：`bestAgent(type)` 在**同类型多实例**之间选分最高的。

## 二、评测：意图 Accuracy + Judge 四维 + baseline

### 1. 入口与用例

`POST /eval/run` → `EndToEndEvaluator.run()`

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
List<IntentCase> intentCases = request.intentCases() != null ? ... : defaultIntentCases();  // 8 条
List<DialogCase> dialogCases = request.dialogCases() != null ? ... : defaultDialogCases();  // 4 条
```

### 2. 意图评测

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
IntentResult result = intentRecognizer.recognize(c.message(), null);
String predicted = result.intent().name().toLowerCase(ROOT);
boolean passed = predicted.equals(c.expectedIntent());   // 精确匹配
```

指标：

```text
intent_accuracy = 命中数 / 用例数
per_class       = 每个类别的 P / R / F1（手写混淆统计）
macro_f1        = 各类 F1 的算术平均（未加权）
```

### 3. 对话评测（LLM-as-Judge）

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
for (String turn : turns) {
    var response = orchestrator.run(AgentRequest.of(turn, userId, convId, history.toString(), history));
    QualityScores scores = judge.judge(turn, response.response(), history.toString());
    boolean passed = scores.overall() >= 0.75;
    history.add(...user...); history.add(...assistant...);
}
```

Judge 的 prompt（`LLMJudge.java:21`）：

```text
你是客服质量评估专家。请对以下客服响应进行评分。
用户问题 / Agent 响应 / 背景信息
从 relevance、accuracy、completeness、helpfulness 四个维度评分，0.0-1.0
只返回 JSON
```

- `temperature=0.0`、`max_tokens=256`；
- 缺字段回退 0.5，异常则四维全 0.5 并标 `judge_failed=true`；
- `overall` = 四维平均，≥0.75 算通过。

```json
  "passed": 8,
  "avg_scores": { "intent_accuracy": 0.75, "macro_f1": 0.69, "dialog_overall": 0.72 },
  "per_class": { "technical": {"precision":0.8,"recall":0.8,"f1":0.8} },
  "regressions": ["intent_accuracy: 0.88 -> 0.75"],
  "recommendations": ["发现评测回归，请对比 baseline ..."],
  "results": [ ...每条用例的输入、输出、分数... ]
}
```

## 三、两个闭环各自的断点（必须主动说）

### 监控闭环：降权其实没生效

```text
penalty → routingScore → bestAgent(type) 择优
                              ↑
                    只在「同类型多实例」之间比较
```

而 `AgentConfig` 里每类只有 1 个实例：

```java
// src/main/java/com/pudding/config/AgentConfig.java
AgentType.GENERAL,   List.of(new GeneralAgent(...)),
AgentType.TECHNICAL, List.of(new TechnicalAgent(...)),
AgentType.BILLING,   List.of(new BillingAgent(...))
```

所以 `routingScore` 没有比较对象，**penalty 改变不了任何路由结果**，实际只起到告警作用。

修法就一行——在 `domainScores` 出来后乘惩罚：

```java
// src/main/java/com/pudding/agent/AgentOrchestrator.java
scores.replaceAll((type, s) -> s * (1 - penaltyOf(type)));
```

### 评测闭环：与线上不同构

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
// 评测里只调了编排器
var response = orchestrator.run(AgentRequest.of(turn, userId, convId, history.toString(), history));
```

它**绕过了**：
- Controller 的 RAG 检索（`searchWithRewrite`）
- `AnswerVerifier` 回答校验
- 记忆读写与画像
- 真实的 `fullContext`（这里传的是 `history.toString()`，一个 List 的 toString）

所以它评的是「Agent 生成质量」，不是「线上端到端效果」。

## 四、其他已知短板

| 问题                                  | 说明                                                         |
| ------------------------------------- | ------------------------------------------------------------ |
| Java 没有 baseline 文件               | `data/eval/` 不存在，第一次 `/eval/run` 才会生成，之前没有回归可比 |
| 标签口径冲突                          | 默认用例期望 `technical`，系统输出 `technical_crash`，判对也记错 |
| 样本太小                              | 8+4，19 类意图大多数没覆盖                                   |
| 对话无参考答案                        | Judge 只能打绝对分，准确性维度基本靠模型自评                 |
| Judge 同源                            | 和被评模型是同一个，存在自评偏好                             |
| baseline 覆盖式                       | 一次坏结果就会污染基线，之后反而看不出退化                   |
| 告警不闭环                            | `alertKeys` 永久去重、`resolved` 恒 false、无恢复通知、webhook 无超时重试 |
| `detectRegressions` 只比 `avg_scores` | `per_class` 退化不会被发现；previous 为 0 时直接跳过         |

## 六、面试版（60 秒）

> 监控这块，每个 Agent 调用结束会记成功与否和耗时，每 10 秒汇总一次，按成功率低于 0.9、延迟高于 3000 毫秒算一个惩罚分，封顶 0.9，写回 Agent 的 routingScore；routingScore 是成功率 0.7 加延迟分 0.3，再乘 1 减惩罚。
> 指标通过 Micrometer 暴露成 Prometheus 格式，有一个 Gauge 是最差 Agent 的成功率，还有采集次数和采集耗时。
> 但我要说清楚，这个降权目前没真正影响路由：routingScore 只在同类型多实例间择优，而现在每类只有一个实例，所以它实际只起告警作用。修法是把惩罚乘进领域打分。
> 评测这块是 8 条意图用例加 4 条对话用例，意图算 Accuracy、每类 P/R/F1 和 Macro-F1，对话用 Judge 从相关性、准确性、完整性、有用性四维打分，0.75 通过；每次跑完和 baseline 比，相对下降超过 5% 标记回归。
> 它的短板是评测绕过了检索、校验和记忆，和线上不同构。



三个问题分别答。

## 一、意图部分：是手写测试集，不是模型生成

Java 版 8 条，硬编码在 `EndToEndEvaluator.defaultIntentCases()`：

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
new IntentCase("我的订单什么时候到？", "query"),
new IntentCase("帮我取消订单",        "request"),
new IntentCase("你们服务太差了！",     "complaint"),
new IntentCase("应用一直500错误",     "technical"),
new IntentCase("为什么扣了两次款？",   "billing"),
new IntentCase("我要投诉，转人工！",   "escalation"),
new IntentCase("你好",                "greeting"),
new IntentCase("修改我的邮箱地址",     "account")
```

跑的方式是**精确匹配**：

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
IntentResult result = intentRecognizer.recognize(c.message(), null);
boolean passed = result.intent().name().toLowerCase().equals(c.expectedIntent());
```

然后算三个指标：

```text
intent_accuracy = 命中 / 总数
per_class       = 每个类别的 precision / recall / F1（手写混淆统计）
macro_f1        = 各类 F1 的算术平均（未加权）
```

**它的定位是「分类回归测试」**：标签是人定的，模型输出对不上就扣分，不涉及任何语义判断。

## 二、LLM-as-Judge：是让模型打分，但流程是固定的

对话评测没有标准答案，所以改用「模型当评委」：

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
QualityScores scores = judge.judge(turn, response.response(), history.toString());
boolean passed = scores.overall() >= 0.75;
```

Judge 的 prompt（`LLMJudge.java:21`）：

```text
你是客服质量评估专家。请对以下客服响应进行评分。
用户问题 / Agent 响应 / 背景信息

从 relevance、accuracy、completeness、helpfulness 四个维度评分，0.0-1.0。
只返回 JSON。
```

四个维度分别是：

| 维度         | 问的问题                   |
| ------------ | -------------------------- |
| relevance    | 回答是不是针对用户这个问题 |
| accuracy     | 信息准确吗                 |
| completeness | 问题解决完整吗             |
| helpfulness  | 用户能不能据此行动         |

工程约束有四道闸：

```java
// src/main/java/com/pudding/evaluation/LLMJudge.java
temperature = 0.0        // 降低抖动
max_tokens  = 256        // 短输出，防止跑题
asDouble(...)            // 分数 clamp 到 [0,1]
catch → 全 0.5 + judgeFailed = true   // 解析失败不崩，但标记
```

`overall` = 四维平均，≥0.75 算通过。

**它评的是「像不像一个好回答」，不是「事实对不对」**——因为 Judge 手里既没有参考答案，也没有知识库片段（传的 context 是对话历史）。这是它最大的局限。

## 三、baseline 回归检测：跟自己的上一次比

### 什么是 baseline

就是一个 JSON 快照，保存**上一次评测的指标**：

```json
{
  "avg_scores": {
    "intent_accuracy": 0.875,
    "macro_f1": 0.69,
    "dialog_overall": 0.72
  },
  "results": [ ...每条用例的输入输出... ]
}
```

路径：`data/eval/baseline.json`（`EVAL_BASELINE_PATH` 可覆盖）。

### 检测流程

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
List<String> regressions = detectRegressions(avgScores);   // ① 先跟旧 baseline 比
...
saveBaseline(report);                                      // ② 再用这次结果覆盖
```

比较逻辑（`EndToEndEvaluator.java:185`）：

```java
// src/main/java/com/pudding/evaluation/EndToEndEvaluator.java
double delta = (current - previous) / previous;
if (delta < -0.05) {
    regressions.add(key + ": " + previous + " -> " + current);
}
```

**相对下降超过 5%，就标记为回归。**

### 一个具体例子

```text
上一次：intent_accuracy = 0.875
这一次：intent_accuracy = 0.750
delta = (0.75 - 0.875) / 0.875 = -14.3%  < -5%
→ regressions = ["intent_accuracy: 0.875 -> 0.75"]
→ recommendations 追加"发现评测回归，请对比 baseline 检查最近 prompt 或检索变更"
```

如果这次是 0.85：

```text
delta = (0.85 - 0.875) / 0.875 = -2.9%  > -5%
→ 不标记回归
```

### 为什么要「跟自己比」，而不是设绝对阈值

- 绝对阈值（比如「准确率必须 > 0.9」）在不同测试集、不同业务下没有可比性；
- 回归检测问的是另一个问题：**「我这次改动，有没有把原本能过的用例搞挂？」**
- 典型触发场景：改 prompt、换模型、调检索参数、动意图权重。跑一次评测，回归列表会直接告诉你哪项掉了。

本质上和单元测试里的「golden file」是一个思路：**先固化一个基准，之后每次和基准比**。

## 四、三部分怎么串起来

```text
POST /eval/run
 ├─ 意图：8 条手写用例 → recognize() → 精确匹配 → accuracy / macro_f1
 ├─ 对话：4 条用例（3 单轮 + 1 三轮）→ orchestrator.run() → Judge 四维 → overall
 ├─ 汇总：pass_rate / total / passed / avg_scores / per_class
 ├─ 回归：读 baseline.json → 相对下降 > 5% 记 regression
 └─ 落盘：用本次 report 覆盖 baseline.json
```

## 五、三个必须知道的坑

1. **Java 版还没有 baseline 文件**：`data/eval/` 目录不存在，所以第一次跑只能「建立基线」，检测不出回归；要跑第二次才有对比。
2. **覆盖式保存会污染基线**：如果某次跑出坏结果（比如模型临时不可用，全 0.5），它会覆盖好基线，下一轮反而看不出退化。正确做法是保留历史版本，或只在人工确认后更新。
3. **只比 `avg_scores` 三项**：`per_class` 里某个类别崩了不会被发现；而且 `previous = 0` 时直接跳过比较，`macro_f1` 从 0 涨上来也检测不到。

## 六、面试版（50 秒）

> 意图部分是手写的 8 条用例，硬编码在代码里，标签是人定的粗粒度意图，跑完做精确匹配，算 accuracy、每类 P/R/F1 和未加权的 Macro-F1。
> 对话部分没有标准答案，所以用 LLM-as-Judge，让模型从相关性、准确性、完整性、有用性四个维度打 0 到 1 的分，取平均，0.75 算通过；温度是 0，解析失败回退 0.5 并标记。
> baseline 回归检测就是先把上一次的指标存成 JSON，每次跑完先跟它比，相对下降超过 5% 就标记为回归，然后用这次结果覆盖。
> 它的价值是回答「这次改动有没有让原本能过的用例挂掉」，但要注意覆盖式保存会被坏结果污染，而且目前只比三个平均指标，类别级退化看不出来。
