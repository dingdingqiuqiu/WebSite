# 商品下单 → 支付（预留） → 二维码核销：订单生命周期与 CAS 并发控制

> 目标：像美团一样「在店里选商品 → 下单 → 支付 → 到店出示二维码核销」，
> 但**不接真实支付**，把支付通道抽象成接口预留出来；同时解决「支付」与「超时关单」并发时订单状态错乱的问题。
>
> 代码位置：`BackEnd/tfshz/src/main/java/com/tfsh/` 下的 `entity/Product*`、`Service/impl/ProductOrderServiceImpl`、
> `pay/`、`task/ProductOrderTimeoutTask`、`controller/Product*`；前端 `devFE/src/views/OrderDetailView.vue` 等。

---

## 0. 先把需求拆成可验证的条目

| 需求 | 落地方式 | 验收标准 |
|---|---|---|
| 店铺里放商品、设置价格 | `tb_product`（价格按「分」存整数） | 103茶餐厅有 7 个商品，`GET /product/of/shop/1` 能取到 |
| 不真调用支付，但预留接口 | `PayService` 接口 + `MockPayService` 实现 + `/pay/notify` 回调入口 | 换成真实通道只改实现类，订单侧代码不动 |
| 买东西流程像美团 | 选商品 → 购物车 → 下单 → 订单页支付 | 下单后库存实扣，订单进入待支付 |
| 支付后可用二维码核销 | 支付成功生成/展示核销码二维码，商家核销台扫码核销 | 同一张码只能核销一次 |
| 定时关闭到期未支付订单并回补库存 | Spring Task 每 60s 扫描 `status=1 and expire_time < now()` | 超时订单变已关闭，库存回到下单前 |
| CAS 乐观锁 + 重试解决支付/关单并发 | 订单表 `version` 字段，所有状态流转都带 `where status=? and version=?` | 并发 10 个请求（5 支付 + 5 关单），每单 `version` 只 +1 一次 |

### 1.2 状态机（只允许这些迁移）

```
          下单（扣库存）
               │
               ▼
         ┌──────────┐  支付(CAS)   ┌──────────┐  核销(CAS)  ┌──────────┐
         │ 1 待支付 │ ───────────▶ │ 2 已支付 │ ──────────▶ │ 3 已核销 │
         └──────────┘              └──────────┘             └──────────┘
            │      │
   用户取消 │      │ 超时（Spring Task）
   (CAS)    │      │ (CAS + 回补库存)
            ▼      ▼
         ┌──────────┐
         │ 4 已关闭 │
         └──────────┘
```

关键约束：**任何一条边都不能被重复走**（不能支付两次、不能核销两次、不能既支付又关闭）。

## 2. 下单：条件更新扣库存 + 事务回滚

`ProductOrderServiceImpl#createOrder`：

```java
// 1. 合并同一商品的数量
Map<Long, Integer> quantities = new LinkedHashMap<>();
for (ProductOrderForm.Item item : form.getItems()) {
    quantities.merge(item.getProductId(), item.getQuantity(), Integer::sum);
}

// 2. 逐个商品做「条件更新」扣库存：库存够才扣，原子且不会扣成负数
boolean deducted = productService.update()
        .setSql("stock = stock - " + quantity)
        .eq("id", product.getId())
        .ge("stock", quantity)          // ← 关键：where stock >= n
        .update();
if (!deducted) {
    // 抛业务异常 → @Transactional 回滚 → 前面已经扣掉的库存一起退回
    throw new BizException("商品「" + product.getName() + "」库存不足，请调整数量");
}

// 3. 生成订单（待支付 + 15 分钟支付截止时间 + 核销码 + version=0）
ProductOrder order = new ProductOrder()
        .setId(redisIdWorker.nextId("porder"))
        .setStatus(OrderStatus.WAIT_PAY)
        .setVerifyCode(nextVerifyCode())
        .setVersion(0)
        .setExpireTime(now.plusMinutes(PAY_TIMEOUT_MINUTES));
save(order);
items.forEach(item -> itemMapper.insert(item.setOrderId(orderId)));
```

三个细节：

1. **为什么不用 `update stock = stock - n where id = ?` 再判影响行数**：那样并发下会扣成负数。加 `stock >= n` 让「检查」和「扣减」变成一条原子 SQL，和秒杀里的写法是同一个套路。
2. **中途失败怎么不留下“多扣”**：整段在 `@Transactional` 里，任何一步抛 `BizException` 都会回滚，包括已经扣掉的库存。
3. **核销码为什么下单就生成**：用户支付后要立刻看到二维码，不能等到支付回调再造码；码是随机的 10 位（去掉 `I/O/0/1` 防看混），`uk_verify_code` 唯一索引兜重复。

### 3.2 支付落状态：与回调走同一条 CAS 路径

```java
public Result payOrder(Long orderId) {
    // ... 归属校验、幂等判断（已支付直接返回成功）、已关闭直接拒绝
    PayResult prepay = payService.prepay(order);          // ① 预下单（预留）
    if (!payService.queryPaid(prepay.getTradeNo())) {      // ② 查单确认
        return Result.fail("支付未完成，请稍后重试");
    }
    return confirmPaidByNotify(orderId, prepay.getTradeNo());  // ③ 和回调同一条 CAS
}

public Result confirmPaidByNotify(Long orderId, String tradeNo) {
    boolean paid = casStatus(orderId, WAIT_PAY, PAID,
            wrapper -> wrapper.set(ProductOrder::getPayTime, LocalDateTime.now()));
    if (!paid) {
        // CAS 失败 → 大概率被定时任务关掉了，重读给出准确结论
        ProductOrder latest = getById(orderId);
        if (latest.getStatus() == CLOSED) return Result.fail("订单已超时关闭，支付未生效");
        if (latest.getStatus() == PAID || latest.getStatus() == VERIFIED) return Result.ok(buildVO(latest));
        return Result.fail("支付失败，请重试");
    }
    return Result.ok(buildVO(getById(orderId)));
}
```

回调入口 `POST /pay/notify`（`PayController`）现在就是转调 `confirmPaidByNotify`。
真实接入时要补三件事（注释里也写了）：**验签**、**把 `/pay/notify` 加进免登录白名单**、**幂等**（同一笔回调可能推多次，CAS 保证只处理一次）。

## 4. 核销：二维码 + 一次核销

- 二维码内容就是 `verify_code`，前端用 `qrcode-generator`（MIT，已 vendored 到 `devFE/src/vendor/qrcode-generator.js`）**本地生成 SVG**，不依赖任何外部图片接口；
- 商家在 `/verify` 核销台输入/扫描核销码：

```java
public Result verify(String code) {
    ProductOrder order = getOne(Wrappers.<ProductOrder>lambdaQuery()
            .eq(ProductOrder::getVerifyCode, code.trim().toUpperCase()), false);
    if (order == null) return Result.fail("核销码不存在");
    if (order.getStatus() == WAIT_PAY) return Result.fail("订单未支付，无法核销");
    if (order.getStatus() == VERIFIED) return Result.fail("该订单已核销，请勿重复核销");
    if (order.getStatus() == CLOSED)  return Result.fail("订单已关闭，无法核销");

    // 同一张码被两台终端同时扫：CAS 保证只有一次成功
    boolean verified = casStatus(order.getId(), PAID, VERIFIED,
            wrapper -> wrapper.set(ProductOrder::getVerifyTime, LocalDateTime.now()));
    if (!verified) return Result.fail("核销失败：订单状态已变化，请重新扫码");
    return Result.ok(buildVO(getById(order.getId())));
}
```

## 5. 订单生命周期：Spring Task 定时关单 + 回补库存

```java
@EnableScheduling          // 启动类上开启
...
@Scheduled(initialDelay = 30_000, fixedDelay = 60_000)
public void scheduledCloseExpiredOrders() { closeExpiredOnce(); }

public int closeExpiredOnce() {
    List<ProductOrder> expired = productOrderService.listExpired(200);  // status=1 and expire_time < now()
    int closed = 0;
    for (ProductOrder order : expired) {
        // 每条走独立事务：CAS 成功才回补库存；失败（已被支付）直接跳过
        if (productOrderService.closeOrder(order.getId())) closed++;
    }
    return closed;
}
```

```java
@Transactional(rollbackFor = Exception.class)
public boolean closeOrder(Long orderId) {
    boolean closed = casStatus(orderId, WAIT_PAY, CLOSED,
            wrapper -> wrapper.set(ProductOrder::getCloseTime, LocalDateTime.now()));
    if (!closed) {
        log.info("[product-order] 关单跳过：状态已变化 orderId={}", orderId);
        return false;                 // 已被支付，绝不能回补库存
    }
    restoreStock(orderId);            // 只有真关掉了才退库存
    return true;
}
```

两个容易踩的坑，这里都刻意规避了：

1. **`@Transactional` 自调用失效**：扫描循环放在 Task 类里，`closeOrder` 放在 Service 里，走的是 Spring 代理，事务才生效（之前秒杀那篇踩过同一个坑）。
2. **CAS 失败不能回补库存**：只有「本次调用真的把状态从 1 改成 4」才退库存，否则会出现「订单已支付、库存却退回去了」的资损。

另外留了 `POST /product-order/task/close-expired` 手动触发一次，便于演示和压测（见第 7 节）。

## 6. 并发控制：版本号 CAS + 重试

### 6.1 核心 SQL

```sql
UPDATE tb_product_order
   SET status = #{target}, version = version + 1, ... 
 WHERE id = #{id} AND status = #{expectStatus} AND version = #{readVersion}
```

影响行数 = 1 表示「本次调用成功完成了状态流转」；= 0 表示有人抢先改了（支付/关单/核销竞争）。

### 6.2 带重试的实现

```java
private boolean casStatus(Long orderId, int expectStatus, int targetStatus,
                          Consumer<LambdaUpdateWrapper<ProductOrder>> extraSets) {
    for (int attempt = 1; attempt <= CAS_MAX_RETRY; attempt++) {   // 最多 3 次
        ProductOrder current = getById(orderId);
        if (current == null || current.getStatus() != expectStatus) return false;   // 状态已变，没必要重试
        LambdaUpdateWrapper<ProductOrder> wrapper = Wrappers.<ProductOrder>lambdaUpdate()
                .eq(ProductOrder::getId, orderId)
                .eq(ProductOrder::getStatus, expectStatus)
                .eq(ProductOrder::getVersion, current.getVersion())   // ← 版本号
                .set(ProductOrder::getStatus, targetStatus)
                .setSql("version = version + 1");
        if (extraSets != null) extraSets.accept(wrapper);
        if (update(wrapper)) return true;                              // 抢到了
        log.warn("[product-order] CAS 冲突 orderId={} 第 {}/{} 次重试", orderId, attempt, CAS_MAX_RETRY);
    }
    return false;
}
```

重试的语义要说清楚：**版本号冲突时重读订单再判断**。
如果重读发现状态已经不是期望值（比如已经被关单），直接返回 `false`，由调用方给出「订单已关闭」这类准确提示，而不是无限重试。

### 6.3 为什么「CAS」能解决支付 / 关单并发

假设同一个订单同时被两个请求处理：

| 时刻 | 支付线程 | 关单线程 | 数据库 |
|---|---|---|---|
| T1 | 读到 `status=1, version=0` | 读到 `status=1, version=0` | 1 / 0 |
| T2 | `UPDATE ... WHERE status=1 AND version=0` → 成功 | —— | **2 / 1** |
| T3 | —— | `UPDATE ... WHERE status=1 AND version=0` → **影响 0 行** | 2 / 1 |
| T4 | —— | CAS 失败 → 不回补库存，跳过 | 2 / 1 |

反过来（关单先赢）也一样：支付会拿到 `status=4`，返回「订单已超时关闭，支付未生效」，且**不会**出现「已关闭却扣了钱」的脏状态。
这就是为什么所有状态迁移都必须走 CAS，而不是 `update status = ? where id = ?`。

### 7.3 支付 vs 关单竞态（每单 10 个并发请求）

3 个已过期订单，每单同时发 **5 次支付 + 5 次关单**：

| 订单 | 最终状态 | version | 支付成功次数 | 说明 |
|---|---|---|---|---|
| …016 | 2 待核销 | 1 | 5（1 次真成功 + 4 次幂等） | 支付赢，不会被关单 |
| …017 | 4 已关闭 | 1 | 0 | 关单赢，支付被拒 |
| …018 | 4 已关闭 | 1 | 0 | 关单赢，支付被拒 |

关键结论：**每单 `version` 只 +1**，说明状态只流转了一次；库存只给「已关闭」的两单各回补 1 件（40 → 37 → 39），支付成功的那单库存保持扣除。

## 8. 踩坑与设计取舍

1. **CAS 失败就回补库存 = 资损**：关闭订单必须先 CAS 成功，再退库存；顺序反了会出现「已支付 + 库存已退」。
2. **`@Transactional` 自调用失效**：任务类里循环调用 Service 的 `closeOrder`，不要写在同一个类里自调用。
3. **订单号精度**：19 位订单号在 JS 里会丢精度，`ProductOrderVO.orderId` 用 `String` 返回（和之前 VoucherOrderVO 一个道理）。
4. **金额一律用「分」**：`int` 存分，前端 `/100` 展示，避免 `0.1 + 0.2` 类问题。
5. **核销码要唯一且随机**：随机 10 位 + 唯一索引；不要用自增 id 或订单号，否则能被猜出来白吃。
6. **Spring Task 只适合单机**：多实例部署时多个节点会同时扫到同一批订单，CAS 保证不会重复关单，但会做无用功；规模上来要换成分布式调度（XXL-JOB）或延迟消息。
7. **定时任务参数**：`fixedDelay`（跑完再计时）而不是 `fixedRate`，避免任务堆积；单次批量上限 200，避免一次扫全表。
8. **支付回调要做验签 + 幂等**：现在 `/pay/notify` 仍要求登录，真实接入时要放开白名单，但必须加签名校验，否则任何人都能把订单改成已支付。

## 11. 统一：秒杀券订单并入同一套生命周期（后续演进）

最初秒杀券只到「抢到 + 落库」为止，和商品订单是两套东西；后来两者被统一成**同一种订单形态**：

| 维度 | 统一前 | 统一后 |
|---|---|---|
| 支付 | 券单不需要支付 | 券单也走 `PayService`（`PayRequest` 抽象，产品/券无差别） |
| 支付截止 | 券单没有 | 与商品单一致：`expire_time = now + 15min` |
| 超时关单 | 只有商品单 | `OrderTimeoutTask` 同时扫 `tb_product_order` 与 `tb_voucher_order` |
| 回补库存 | 只有商品单 | 券单回补要**双写**：DB `stock + 1` + Redis `INCR` + 从「已下单集合」`SREM`（允许该用户重新抢） |
| 核销 | 只有商品单 | 一个核销台：核销码带前缀（`P` 商品 / `V` 券），`POST /order/verify/{code}` 据此定位订单表 |
| 并发 | 只有商品单有 CAS | 券单加 `version` 列，支付/取消/核销/关单全部走同一套 `casStatus` |
| 前端 | 「我的优惠券」和「我的订单」两个列表 | 「我的订单」一条流，用类型徽标区分，共用 `/orders/{type}/{id}` 页面 |

改动清单：
- `tb_voucher_order` 增列：`verify_code`、`version`、`expire_time`、`close_time`（`pay_time`/`use_time` 复用）；
- `VoucherOrderServiceImpl` 补齐 `payOrder / confirmPaid / cancelOrder / closeOrder / listExpired / verifyByCode`；
- 新增 `OrderVerifyService`（统一核销）与 `SeckillStockRollback`（Redis 预扣回滚组件，三处失败路径复用）；
- `ProductOrderTimeoutTask` 升级为 `OrderTimeoutTask`；
- 抢券接口的返回从 `number` 改成 `string`：19 位订单号用 number 会让前端丢精度（这是联调时踩到的真问题）。
