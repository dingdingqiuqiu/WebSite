```java
        public <R, ID> R queryWithMultiLevel(
            String keyPrefix, ID id, Type type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
        String key = keyPrefix + id;
        // 1.查本地缓存（纳秒级，命中即返回，完全不依赖 Redis）
        Object local = LOCAL_CACHE.getIfPresent(key);
        if (local != null) {
            return JSONUtil.toBean(local.toString(), type);
        }
        // 2.查 Redis（逻辑过期：key 永不物理过期，过期时间内嵌在 value 中）
        String json = stringRedisTemplate.opsForValue().get(key);
        R r = null;
        if (StrUtil.isNotBlank(json)) {
            RedisData redisData = JSONUtil.toBean(json, RedisData.class);
            r = JSONUtil.toBean((JSONObject) redisData.getData(), type);
            if (redisData.getExpireTime().isAfter(LocalDateTime.now())) {
                // 2.1.未过期：回填本地后返回
                LOCAL_CACHE.put(key, r);
                return r;
            }
            // 2.2.已逻辑过期：互斥锁 + 异步重建，本线程直接返回旧数据
            //     （击穿防护核心：海量并发中只有一个线程查库，其余请求拿旧数据返回，可用性优先）
            String lockKey = LOCK_SHOP_KEY + id;
            if (tryLock(lockKey)) {
                CACHE_REBUILD_EXECUTOR.submit(() -> {
                    try {
                        R newR = dbFallback.apply(id);
                        if (newR != null) {
                            this.setWithLogicalExpire(key, newR, time, unit);
                        }
                    } catch (Exception e) {
                        throw new RuntimeException(e);
                    } finally {
                        unlock(lockKey);
                    }
                });
            }
        } else {
            // 3.Redis 无数据（首次访问/冷启动）：同步查库回源并写入
            r = dbFallback.apply(id);
            if (r != null) {
                this.setWithLogicalExpire(key, r, time, unit);
            }
        }
        // 4.回填本地缓存（旧数据也回填：5 秒后本地自动过期，很快会被新数据替换）
        if (r != null) {
            LOCAL_CACHE.put(key, r);
        }
        return r;
    }

```

要点解读：

- **步骤 2.2 是整个击穿防护的语义核心**：拿到旧数据就直接返回、绝不等待，重建交给后台线程池——与已有的 `queryWithLogicalExpire` 语义一致，只是外层多包了一层本地缓存。
- **为什么传 `Type` 而不是 `Class<R>`**：`Voucher[]` 列表要反序列化成 `List<Voucher>`，`List.class` 会得到 `List<JSONObject>`，泛型信息丢失。用 `TypeReference` 把泛型带进去。
- **步骤 3 是冷启动路径**：Redis 完全没数据时没有"旧数据"可返回，只能同步回源。击穿防护防的是"有旧数据但过期了"的瞬间，两条路径分工不同。

### 4.4 新增 `utils/CacheDeleteCompensator.java`

完整文件（结构与秒杀订单的 `VoucherOrderHandler` 同款模式，方便你对照理解）：

```java
package com.tfsh.utils;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.Resource;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.connection.stream.*;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

import static com.tfsh.utils.RedisConstants.*;

/**
 * 缓存删除补偿器：保证"更新数据库后删除缓存"的最终执行。
 *
 * 原理（第一性）：
 *   1. 删除缓存天然幂等（删两次 = 删一次），所以消息重复消费没有副作用——
 *      这是"补偿"能用消息队列实现的根本原因，也是消息里只放 key、不放数据的原因；
 *   2. 删除失败 -> 写一条消息到 Redis Stream，消费者异步重试；
 *   3. 梯度退避：1s、2s、4s……上限 60s，最多重试 CACHE_DELETE_MAX_RETRY 次；
 *   4. 重试耗尽仍失败 -> 记录 error 日志告警，人工介入（缓存自身的 TTL 是最后兜底）。
 */
@Slf4j
@Component
public class CacheDeleteCompensator {

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    private static final ExecutorService CONSUMER_EXECUTOR = Executors.newSingleThreadExecutor();

    @PostConstruct
    private void init() {
        // 创建消费者组（组已存在时 Redis 返回 BUSYGROUP 错误，忽略即可）
        try {
            stringRedisTemplate.opsForStream().createGroup(CACHE_DELETE_STREAM, CACHE_DELETE_GROUP);
        } catch (Exception e) {
            // 组已存在
        }
        CONSUMER_EXECUTOR.submit(new CacheDeleteHandler());
    }

    /**
     * 删除缓存；删除失败（网络抖动等异常）时发送补偿消息，由消费者梯度重试。
     * 注意：key 不存在时 delete 返回 false，同样视为删除成功——缓存本来就不在，目标已达成。
     */
    public void delete(String key) {
        try {
            stringRedisTemplate.delete(key);
        } catch (Exception e) {
            log.error("删除缓存失败，已发送补偿消息：{}", key, e);
            send(key, 0);
        }
    }

    private void send(String key, int retry) {
        Map<String, Object> msg = Map.of(
                "key", key,
                "retry", String.valueOf(retry),
                "ts", String.valueOf(System.currentTimeMillis()));
        stringRedisTemplate.opsForStream().add(
                StreamRecords.newRecord().ofMap(msg).withStreamKey(CACHE_DELETE_STREAM));
    }

    private class CacheDeleteHandler implements Runnable {

        @Override
        public void run() {
            while (true) {
                try {
                    // 1.读取补偿消息 XREADGROUP GROUP g-cache c-cache COUNT 1 BLOCK 2000 STREAMS stream.cache-delete >
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from(CACHE_DELETE_GROUP, "c-cache"),
                            StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
                            StreamOffset.create(CACHE_DELETE_STREAM, ReadOffset.lastConsumed()));
                    // 2.无消息则继续等待
                    if (list == null || list.isEmpty()) {
                        continue;
                    }
                    // 3.处理消息
                    handle(list.get(0));
                } catch (Exception e) {
                    log.error("消费补偿消息异常", e);
                    handlePending();
                }
            }
        }

        /** 处理消费失败堆积的消息（未被 XACK 的消息会进入 pending-list） */
        private void handlePending() {
            while (true) {
                try {
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from(CACHE_DELETE_GROUP, "c-cache"),
                            StreamReadOptions.empty().count(1),
                            StreamOffset.create(CACHE_DELETE_STREAM, ReadOffset.from("0")));
                    if (list == null || list.isEmpty()) {
                        break;
                    }
                    handle(list.get(0));
                } catch (Exception e) {
                    log.error("处理 pending-list 异常", e);
                    break;
                }
            }
        }

        private void handle(MapRecord<String, Object, Object> record) {
            Map<Object, Object> value = record.getValue();
            String key = (String) value.get("key");
            int retry = Integer.parseInt((String) value.get("retry"));
            try {
                // 删除缓存（key 不存在视为成功）
                stringRedisTemplate.delete(key);
                // 删除成功 -> 确认消息 XACK
                stringRedisTemplate.opsForStream().acknowledge(CACHE_DELETE_STREAM, CACHE_DELETE_GROUP, record.getId());
            } catch (Exception e) {
                if (retry + 1 >= CACHE_DELETE_MAX_RETRY) {
                    // 重试耗尽：告警，人工介入；先 XACK 避免 pending-list 无限堆积
                    log.error("删除缓存重试已达 {} 次，请人工介入：{}", CACHE_DELETE_MAX_RETRY, key, e);
                    stringRedisTemplate.opsForStream().acknowledge(CACHE_DELETE_STREAM, CACHE_DELETE_GROUP, record.getId());
                } else {
                    try {
                        // 梯度退避：1s、2s、4s……上限 60s
                        Thread.sleep(Math.min(1000L << retry, 60_000L));
                    } catch (InterruptedException ie) {
                        Thread.currentThread().interrupt();
                    }
                    // 确认旧消息，发送一条带新重试次数的消息
                    stringRedisTemplate.opsForStream().acknowledge(CACHE_DELETE_STREAM, CACHE_DELETE_GROUP, record.getId());
                    send(key, retry + 1);
                }
            }
        }
    }
}
```

设计说明：

- **为什么用 Redis Stream 而不是 Kafka**：本项目技术栈里已经有 Redis Stream（秒杀订单 `stream.orders` 同款消费者组模式），零新组件、学习成本最低；话术第 87 行原话——"方案的选择要考虑团队技术栈"。若团队已有 Kafka，把 `send` 换成 `KafkaTemplate.send`、消费者换成 `@KafkaListener` 即可，补偿思路完全一致（见 4.7 对照代码）。
- **梯度退避的 sleep 在单线程消费者里会阻塞其他消息**：补偿消息只在"删除失败"时产生，量极小，可接受；生产环境建议换 RabbitMQ 死信队列 / RocketMQ 延迟消息，天然支持延迟重试。

## 7. 坑与安全清单

1. **`delete` 不存在的 key 返回 false/0，不是失败**：这是本模块最容易踩的坑——如果把"返回 0"当成删除失败，会陷入无限重试。本指南的生产者和消费者都按"返回 0 视为成功（缓存本来就不在，目标已达成）"处理。
2. **逻辑过期返回的是旧数据**：强一致业务（金融）必须用互斥锁方案（`queryWithMutex` 已备好）。本项目是社交媒体类业务，可用性优先，选逻辑过期——这正是话术第 29-33 行的取舍，面试必问，答案要背熟。
3. **本地缓存靠短 TTL 自愈，不要做广播失效**：集群各实例本地副本的一致性靠"5 秒过期"解决，比消息广播简单一个数量级（话术 110-111 行）。
4. **重建必须用独立线程池**（`CACHE_REBUILD_EXECUTOR`）：逻辑过期方案里重建在后台做，请求线程只拿旧数据返回；把重建放进请求线程会让接口被拖慢，击穿防护形同虚设。
5. **逻辑过期的 key 无物理 TTL → 内存常驻**：热点 key 需要预热（活动上线前先查一次/启动时加载），且只对真正的热点数据用逻辑过期，普通数据用物理 TTL（话术 14-16 行：先预热再上量）。
6. **补偿消息只放 key，不放数据**：删除是幂等的，所以重复消费无害；但如果消息里带数据（比如"重建缓存"型任务）就失去了幂等性。这是"补偿可以用 MQ"的合法性边界。
7. **泛型反序列化必须传 `Type`**：`queryWithMultiLevel` 特意把参数设计成 `Type`，调用方用 `new TypeReference<List<Voucher>>() {}.getType()`，否则拿到的是 `List<JSONObject>`。
8. **单线程消费者 + sleep 退避**：补偿消息量极小可接受；生产建议换 RabbitMQ 死信队列 / RocketMQ 延迟消息（4.7 给了 Kafka 对照）。
9. **本地缓存必须设 maximumSize**：防内存无界增长 OOM。10_000 条 × 券列表大小完全可控。
10. **先更新库、后删缓存**的顺序不能反（原理见 2.4）；且删缓存要在事务提交后执行，避免"库回滚了缓存却删了"（删了无害，但不删也无害——库没变）。
11. **TTL 是最后一道防线**：补偿耗尽、人工没来之前，物理 TTL（商铺 30 分钟）保证旧数据不会永久驻留。逻辑过期的券列表缓存没有物理 TTL，因此它的"兜底"是——新增/更新券时必须走到删缓存逻辑（4.6 ③），不能漏。
12. **日志即告警**：`CacheDeleteCompensator` 的 error 日志要接入监控系统，否则"人工介入"永远不会发生（话术 90-91 行）。
