# 高并发秒杀：Redis 预扣 + Lua 原子 + Stream 异步落库

> 目标：把"抢券"这条链路做成**不超卖、不丢单、一人一单、可重试、可对账**。
> 代码位置：`BackEnd/tfshz/src/main/java/com/tfsh/seckill/`、`BackEnd/tfshz/src/main/resources/lua/`。

---

## 0. 先立四个不变量

写代码之前先把"什么绝对不能发生"写清楚，后面每一层设计都对着这四条验收：

| 不变量 | 靠什么保证 |
|---|---|
| **不超卖**：卖出的订单数 ≤ 库存 | Redis 预扣（Lua 原子）+ DB 条件更新 `stock > 0` + 唯一索引 |
| **一人一单**：同一用户同一张券只能抢到一次 | Lua 里的 `SISMEMBER` 前置拦截 + Redisson 锁 + DB 唯一索引 |
| **不丢单**：抢到资格的用户一定会有订单 | Stream 持久化 + 消费者组 + XACK + Pending List 重试 |
| **可对账**：失败的单有痕迹 | 预扣回滚 Lua + 死信队列 `stream.orders.dlq` |

关键取舍：**同步链路里绝不做数据库写**。Redis 里两步（扣库存、入队）成功后立刻返回订单号，DB 写放给消费者，这样接口 RT 只取决于 Redis。

## 1. 数据流（一张图看完）

```
POST /voucher-order/seckill/{voucherId}
        │
        ▼
┌───────────────────────────── 同步（请求线程，只碰 Redis）─────────────────────────────┐
│ 1. LoginInterceptor 校验 access token → UserHolder                                    │
│ 2. SeckillStockWarmer.warmUpIfAbsent：库存 key 不在就从 DB 预热一次                    │
│ 3. RedisIdWorker.nextId("order") 生成全局订单号（时间戳+序列号）                        │
│ 4. EVAL seckill.lua  ← 一次 RPC 内完成：时间窗 → 一人一单 → 库存预扣 → XADD 入队         │
│ 5. 返回 orderId（此时订单还没落库）                                                    │
└───────────────────────────────────────────────────────────────────────────────────────┘
        │  stream.orders（消费者组 seckill-group）
        ▼
┌───────────────────────────── 异步（消费者线程池）─────────────────────────────────────┐
│ 6. StreamMessageListenerContainer 拉新消息（XREADGROUP ... >）                         │
│ 7. SeckillOrderProcessor：解析 → SeckillOrderPersistService.persist()                  │
│      · 幂等（orderId 已存在 → 直接成功）                                               │
│      · Redisson 锁 lock:order:{voucherId}:{userId}                                     │
│      · 条件更新 stock = stock - 1 WHERE stock > 0                                      │
│      · INSERT（唯一索引 uk_user_voucher 兜底）                                          │
│ 8. 成功 → XACK；业务失败 → 回滚预扣 + 死信 + XACK；瞬时失败 → 不 ACK，留在 PEL           │
└───────────────────────────────────────────────────────────────────────────────────────┘
        │
        ▼
   每 30s 扫 Pending List：空闲 > 60s 的消息 XCLAIM 认领重试，投递 ≥ 5 次进死信
```

## 2. Redis key 设计

`utils/RedisConstants.java` 新增：

```java
// ============ 秒杀：Redis 预扣库存 + Stream 异步下单 ============
/** 一人一单集合：seckill:order:{voucherId} -> Set<userId>，Lua 里做资格校验 */
public static final String SECKILL_ORDER_KEY = "seckill:order:";
/** 活动元信息：seckill:meta:{voucherId} -> hash{begin,end}，毫秒时间戳，Lua 里校验时间窗 */
public static final String SECKILL_META_KEY = "seckill:meta:";
/** 订单消息流（Stream），Lua 里 XADD 入队 */
public static final String SECKILL_ORDER_STREAM = "stream.orders";
/** 消费者组名 */
public static final String SECKILL_ORDER_GROUP = "seckill-group";
/** 死信队列：重试耗尽或业务失败（DB 库存不足/重复下单）的消息落这里，便于人工对账 */
public static final String SECKILL_ORDER_DLQ = "stream.orders.dlq";
/** 下单锁（Redisson）：lock:order:{voucherId}:{userId}，落库侧的一人一单兜底 */
public static final String SECKILL_LOCK_KEY = "lock:order:";
/** 单条消息最多投递次数，超过进死信 */
public static final long SECKILL_MAX_DELIVERY = 5L;
/** pending 消息空闲多久才允许认领（秒）：必须大于单条处理耗时，否则会抢走别人正在处理的消息 */
public static final long SECKILL_PENDING_IDLE_SECONDS = 60L;
```

| key | 类型 | 作用 | 为什么放 Redis |
|---|---|---|---|
| `seckill:stock:{id}` | String | 剩余库存 | 扣减必须是原子的，DB 行锁扛不住热点行 |
| `seckill:order:{id}` | Set | 抢到资格的用户 | 一人一单前置校验，O(1) |
| `seckill:meta:{id}` | Hash | 活动起止时间（毫秒） | 让时间窗校验也在 Lua 里，省一次 DB 查询 |
| `stream.orders` | Stream | 订单消息 | 持久化队列 + 消费者组 + PEL，天生支持重投 |
| `stream.orders.dlq` | Stream | 死信 | 失败可对账，不丢痕迹 |
| `lock:order:{v}:{u}` | Redisson | 落库串行化 | 分布式锁，带看门狗续期 |

## 3. `lua/seckill.lua`：一次 EVAL 干完四件事

```lua
local stockKey = KEYS[1]     -- seckill:stock:{voucherId}
local orderKey = KEYS[2]     -- seckill:order:{voucherId}
local metaKey = KEYS[3]      -- seckill:meta:{voucherId}
local streamKey = KEYS[4]    -- stream.orders

local userId = ARGV[1]
local voucherId = ARGV[2]
local orderId = ARGV[3]
local now = tonumber(ARGV[4])

-- 1. 库存：key 不存在时 GET 返回 false，tonumber(false) 得到 nil，
--    后面直接比较会抛 "attempt to compare nil with number"，所以必须显式兜成 -1
local stock = tonumber(redis.call('get', stockKey) or '-1')
if stock == nil or stock < 0 then
    return -2
end

-- 2. 时间窗
local beginTime = redis.call('hget', metaKey, 'begin')
local endTime = redis.call('hget', metaKey, 'end')
if beginTime and now < tonumber(beginTime) then
    return 3
end
if endTime and now > tonumber(endTime) then
    return 4
end

-- 3. 一人一单
if redis.call('sismember', orderKey, userId) == 1 then
    return 2
end

-- 4. 库存不足
if stock <= 0 then
    return 1
end

-- 5. 预扣库存 + 6. 记录下单用户 + 7. 订单入队
redis.call('decr', stockKey)
redis.call('sadd', orderKey, userId)
redis.call('xadd', streamKey, '*',
        'orderId', orderId,
        'userId', userId,
        'voucherId', voucherId,
        'createTime', now)

return 0
```

返回值约定（Java 侧一一对应）：

| 返回 | 含义 | 接口响应 |
|---|---|---|
| `0` | 抢到资格 | `Result.ok(orderId)` |
| `1` | 库存不足 | `库存不足` |
| `2` | 重复下单 | `不能重复下单` |
| `3` / `4` | 未开始 / 已结束 | `秒杀尚未开始` / `秒杀已经结束` |
| `-2` | 库存未预热 | `秒杀活动未就绪` |

### 为什么必须是一段 Lua

1. **原子性**：Redis 执行脚本期间不处理其他命令，"查库存 → 查是否下单 → 扣库存 → 入队"之间不可能被别的请求插入，不需要任何分布式锁；
2. **省 RTT**：4 次网络往返压缩成 1 次。QPS 高的时候，RTT 就是并发量；
3. **一致性**：不会出现"扣了库存但没入队"（进程崩在两条命令之间）这种半截状态 —— 这才是"预扣"敢放在 Redis 里的原因。

### 三个易错点（都踩过）

1. **`tonumber(redis.call('get', k))`**：key 不存在时 `GET` 返回 `false`，`tonumber(false)` 是 `nil`，`nil <= 0` 直接抛 Lua 错误，前端看到 500。必须 `or '-1'` 兜底，并显式判 `-2`。
2. **`XADD key * ...`**：`*` 由 Redis 生成时间序列 ID。Redis 7 用效果复制（effects replication），脚本里可以这么写；老版本 Redis 5 之前会因"写入了非确定性命令"报错。
3. **KEYS 与 ARGV 分工**：key 一律走 `KEYS`（集群模式下用来算 slot），参数走 `ARGV`。把 key 拼进 ARGV 在单机没事，上集群会被 CROSSSLOT 打脸。

## 4. `lua/seckill_rollback.lua`：预扣回滚

异步落库阶段发现"DB 库存其实不够"或"用户其实已经买过"时，必须把预扣退回去，否则库存会被失败订单慢慢吃光：

```lua
local stockKey = KEYS[1]
local orderKey = KEYS[2]
local userId = ARGV[1]

redis.call('incr', stockKey)
redis.call('srem', orderKey, userId)
return 1
```

`INCR` 和 `SREM` 放同一个脚本，避免"只退库存、用户还在集合里"的半截状态。

## 5. 库存预热：`SeckillStockWarmer`

**为什么必须有**：Lua 第一步就是 `GET stock`，key 不在就直接 `-2`。也就是说"没预热 = 秒杀直接不可用"。

两个入口：

```java
@Component
public class SeckillStockWarmer implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) { warmUpAll(); }   // ① 启动全量预热

    /** 幂等：库存 key 已存在就跳过，否则重启一次就把运行中扣减过的库存重置回 DB 值 */
    public void warmUp(SeckillVoucher voucher) {
        String stockKey = RedisConstants.SECKILL_STOCK_KEY + voucher.getVoucherId();
        if (!Boolean.TRUE.equals(stringRedisTemplate.hasKey(stockKey))) {
            stringRedisTemplate.opsForValue().set(stockKey, String.valueOf(voucher.getStock()));
        }
        // begin / end 一起写进 meta，Lua 才能做时间窗校验
        stringRedisTemplate.opsForHash().putAll(RedisConstants.SECKILL_META_KEY + id, meta);
    }

    /** ② 懒预热：请求打进来发现 key 不在（Redis 被清过）就从 DB 拉一次 */
    public boolean warmUpIfAbsent(Long voucherId) { ... }
}
```

`VoucherServiceImpl.addSeckillVoucher` 新建秒杀券后也调用 `warmUp`，保证新券立刻可抢。

## 6. 下单入口：`VoucherOrderServiceImpl.seckillVoucher`

```java
@Override
public Result seckillVoucher(Long voucherId) {
    UserDTO user = UserHolder.getUser();
    if (user == null) return Result.fail("请先登录");
    if (!stockWarmer.warmUpIfAbsent(voucherId)) return Result.fail("秒杀券不存在");

    long orderId = redisIdWorker.nextId("order");
    Long code;
    try {
        code = stringRedisTemplate.execute(
                SECKILL_SCRIPT,
                List.of(SECKILL_STOCK_KEY + voucherId,
                        SECKILL_ORDER_KEY + voucherId,
                        SECKILL_META_KEY + voucherId,
                        SECKILL_ORDER_STREAM),
                user.getId().toString(), voucherId.toString(),
                String.valueOf(orderId), String.valueOf(System.currentTimeMillis()));
    } catch (Exception e) {
        // 脚本/Redis 异常不能让用户白等：降级同步下单，仍受条件更新 + Redisson 锁保护
        log.error("[seckill] Lua 执行异常，降级为同步下单", e);
        return createOrderNow(orderId, user.getId(), voucherId);
    }

    return switch (code == null ? -2 : code.intValue()) {
        case 0 -> Result.ok(orderId);          // 抢到资格，异步落库
        case 1 -> Result.fail("库存不足");
        case 2 -> Result.fail("不能重复下单");
        case 3 -> Result.fail("秒杀尚未开始");
        case 4 -> Result.fail("秒杀已经结束");
        default -> Result.fail("秒杀活动未就绪");
    };
}
```

同步降级路径 `createOrderNow` 直接调 `persistService.persist(order)`，能力等价、只是慢。它存在的意义是：**Lua 挂了不等于业务挂了**，此时系统退化成"慢但正确"的 DB 扣减模式。

> 这条降级路径**不能**在 Redis 整体不可用时救命（Redisson 锁也在 Redis 上），它的定位是"脚本/单命令异常"的容错，不要指望它扛 Redis 宕机。

## 7. 落库：`SeckillOrderPersistService`（防超卖的第二道闸门）

```java
@Transactional(rollbackFor = Exception.class)
public PersistOutcome persist(VoucherOrder order) {
    // ① 幂等：消息重复投递（消费者崩溃、pending 重投）时落过库就直接成功
    if (voucherOrderMapper.selectById(order.getId()) != null) return ALREADY_EXISTS;

    // ② 一人一单：Redisson 锁把"同一用户 + 同一张券"的落库串行化
    RLock lock = redissonClient.getLock(SECKILL_LOCK_KEY + voucherId + ":" + userId);
    boolean locked = lock.tryLock(3, 15, TimeUnit.SECONDS);
    if (!locked) throw new SeckillRetryLaterException("获取下单锁超时");   // 可重试，不 ACK

    try {
        // 查历史订单（放在锁里才不会两个并发消息同时通过）
        if (count(userId, voucherId) > 0) return USER_DUPLICATE;

        // ③ 条件更新：库存 > 0 才扣。原子，且永远不会把 stock 扣成负数
        boolean deducted = seckillVoucherService.update()
                .setSql("stock = stock - 1")
                .eq("voucher_id", voucherId)
                .gt("stock", 0)
                .update();
        if (!deducted) return STOCK_EXHAUSTED;      // Redis 预扣和 DB 不同步

        try {
            voucherOrderMapper.insert(order);
        } catch (DuplicateKeyException e) {
            // 唯一索引 uk_user_voucher 兜住并发重复：库存扣减必须一起回滚
            TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
            return USER_DUPLICATE;
        }
        return SUCCESS;
    } finally {
        if (locked && lock.isHeldByCurrentThread()) lock.unlock();
    }
}
```

为什么是"条件更新 + Redisson 锁"两个都要：

- **只有锁**：锁是 Redis 的，Redis 抖动/锁过期会漏；而且锁只保护"一人一单"，不保护库存。
- **只有条件更新**：`stock > 0` 只保证不超卖，不保证一人一单（同一用户并发两条消息都能扣成功）。
- 两者叠加，再加 DB 唯一索引 `uk_user_voucher(user_id, voucher_id)` 做最后兜底，才是完整的。

配套迁移（已执行，并同步进 `DB/tfshz.sql`）：

```sql
ALTER TABLE tb_voucher_order ADD UNIQUE INDEX uk_user_voucher (user_id, voucher_id);
```

`@Transactional` 必须落在**独立 bean** 上：老代码把 `createVoucherOrder` 写成同类私有方法自调用，Spring AOP 代理根本不生效，扣库存和插订单是两条独立事务 —— 插订单失败时库存不会回滚。

## 8. 消费者：`SeckillOrderStreamConsumer`

### 8.1 为什么用 `StreamMessageListenerContainer` 而不是手写 `while(true)`

老的实现是一个 `Executors.newSingleThreadExecutor()` + `while(true) { XREADGROUP ... }`，问题：

- 没有优雅停机（线程是死循环，`@PreDestroy` 停不掉）；
- 消费者名写死 `c1`，多实例部署时同名消费者的 PEL 会混在一起；
- `handlePendingList()` 里 `while(true)` 重读 0 号位，遇到一条永远处理不了的消息就死循环，把新消息全堵住。

现在改成 Spring 的容器：`pollTimeout(2s)`、`batchSize(16)`、**手动 ACK**（`receive` 而不是 `receiveAutoAck`），停机时 `container.stop()`。

```java
@PostConstruct
public void start() {
    ensureConsumerGroup();                     // 组不存在就建（含"流不存在"的兜底）
    container = StreamMessageListenerContainer.create(connectionFactory, options);
    container.receive(
        Consumer.from(SECKILL_ORDER_GROUP, consumerName),   // 消费者名带 hostname + uuid
        StreamOffset.create(SECKILL_ORDER_STREAM, ReadOffset.lastConsumed()),
        this);                                              // 手动 ACK
    container.start();

    pendingReclaimer.scheduleWithFixedDelay(this::reclaimIdlePending, 30, 30, TimeUnit.SECONDS);
}

@Override
public void onMessage(MapRecord<String, String, String> message) {
    processor.handle(message.getId(), toStringMap(message.getValue()), 1L);   // 首次投递 = 1
}
```

### 8.2 建组：流不存在时先"造"出来

`XGROUP CREATE` 在 key 不存在时会报错，而 Spring 的 `createGroup` 不支持 `MKSTREAM`。做法是塞一条占位消息 → 建组（从 `0` 开始，保证不漏消息）→ 删掉占位：

```java
if (!Boolean.TRUE.equals(stringRedisTemplate.hasKey(SECKILL_ORDER_STREAM))) {
    RecordId bootstrap = ops.add(StreamRecords.newRecord().ofMap(Map.of("bootstrap", "1"))
            .withStreamKey(SECKILL_ORDER_STREAM));
    ops.createGroup(SECKILL_ORDER_STREAM, ReadOffset.from("0"), SECKILL_ORDER_GROUP);
    ops.delete(SECKILL_ORDER_STREAM, bootstrap);
}
```

### 8.3 Pending List：消息不丢的真正保证

`XREADGROUP ... >` **只投递从未投递过的消息**。如果消费者拿到消息后进程崩了、或者处理时抛异常没 ACK，这条消息就永远留在该消费者的 PEL 里 —— 新消息继续进来，它再也不会被读到。

所以必须有一个扫 PEL 的补偿任务：

```java
private void reclaimIdlePending() {
    PendingMessages pending = ops.pending(STREAM, GROUP, Range.unbounded(), 100);
    for (PendingMessage message : pending) {
        if (message.getElapsedTimeSinceLastDelivery().getSeconds() < 60) continue;  // 别抢正在处理的
        List<MapRecord<String, Object, Object>> claimed = ops.claim(
                STREAM, GROUP, consumerName, Duration.ofSeconds(60), message.getId());  // XCLAIM 转移所有权
        long deliveryCount = message.getTotalDeliveryCount() + 1;
        for (var record : claimed) processor.handle(record.getId(), toStringMap(record.getValue()), deliveryCount);
    }
}
```

三个参数的含义要清楚：

- **空闲阈值 60s**：`XCLAIM` 只看"这条消息空闲了多久"，设小了会把别的实例正在处理的消息抢走；
- **30s 扫描周期**：重试延迟 ≈ 阈值 + 周期；
- **投递次数**：`XPENDING` 里的 delivery-count，超过 `SECKILL_MAX_DELIVERY` 就判定为毒消息，回滚 + 死信 + ACK，避免它堵住整个队列。

## 9. 处理器：`SeckillOrderProcessor`

结果到动作的映射表（这就是"什么该 ACK、什么不该"的完整规则）：

| 落库结果 | 含义 | 动作 |
|---|---|---|
| `SUCCESS` | 成功 | XACK |
| `ALREADY_EXISTS` | orderId 已落库（重复投递） | XACK（幂等） |
| `USER_DUPLICATE` | DB 已有一单 | 回滚预扣 → 死信 → XACK |
| `STOCK_EXHAUSTED` | DB 库存不够 | 回滚预扣 → 死信 → XACK |
| 可重试异常（抢锁超时、DB 抖动） | 暂时不行 | **不 ACK**，留在 PEL，等认领重试 |
| 投递次数 ≥ 5 | 毒消息 | 回滚 → 死信 → XACK |

```java
if (deliveryCount >= SECKILL_MAX_DELIVERY) {
    rollbackStock(order);
    deadLetter(recordId, body, "重试耗尽：" + e.getMessage());
    acknowledge(recordId);          // 业务上放弃，但一定要 ACK，否则队列永远堵着
} else {
    log.warn("第 {} 次处理失败，留待重试 orderId={}", deliveryCount, order.getId());
    // 不 ACK
}
```

死信消息保留原始字段 + `recordId` + `reason` + `failedAt`，方便人工补单或退款对账。

| 指标 | 结果 |
|---|---|

| `tb_voucher_order` 行数 | `50` |
| 去重用户数 | `50` |
| `seckill:stock:100` | `0` |
| `SCARD seckill:order:100` | `50` |
| Stream 长度 | `50`（只有抢到资格的才入队） |
| `XPENDING` | `0`（全部 ACK） |
| 死信 | `0` |

### 场景 2：同一用户并发 10 次

```
users: 10   success: 1   failed: 9   failReasons: { "不能重复下单": 9 }
```

Lua 里的 `SISMEMBER` 在入队前就拦住了，队列里只会有一条消息。

### 场景 3：故意制造 Redis / DB 库存不一致（验证条件更新兜底）

把 Redis 库存设成 10、DB 库存设成 3，再让 10 个不同用户来抢：

```
Lua 侧: success: 10  （Redis 认为有 10 个名额）
DB 侧 : 落库成功 3 单，其余 7 单 STOCK_EXHAUSTED
结果  : DB stock=0，Redis stock 回滚 10 → 7，死信队列 7 条
```

这就是"第二道闸门"的价值：即使预扣算错了，DB 也绝不会超卖，而且多扣的库存会被自动退回。

### 场景 4：消息卡在 Pending List（验证不丢单）

停掉后端，手工 `XADD` 一条订单消息，再用另一个消费者 `ghost` `XREADGROUP` 读走但**不 ACK**（等价于"消费者读到消息后进程崩了"）：

```
启动前：XPENDING = 1（owner = ghost）
启动后：约 60s 空闲后认领 → 落库成功 → XACK
结果  : 订单在 DB 里出现，XPENDING = 0，DB stock 5 → 4
```

### 场景 5：DB 已有订单但 Redis 记录被清掉（验证一人一单兜底）

`SREM` 掉某个已购用户的 Redis 记录再让他抢：

```
Lua: 放行（Redis 不知道他买过）
落库: count(user, voucher) > 0 → USER_DUPLICATE
动作: 回滚预扣（stock 3 → 4）+ 死信 + XACK
结果: DB 仍然只有 1 条订单，没有重复插入
```

## 12. 踩坑清单

1. **`tonumber(false)`**：库存 key 不存在时 `GET` 返回 `false`，`nil <= 0` 直接抛 Lua 错误 → 接口 500。必须 `or '-1'` 并区分 `-2`。
2. **忘记预热**：同上，所有券都要在启动/新建/懒加载三个时机写进 Redis，且**已存在不覆盖**。
3. **`createVoucherOrder` 自调用 + `@Transactional` 失效**：老代码是私有方法自调用，事务注解不生效，扣库存与插订单各提交一次。必须拆到独立 bean。
4. **只读 `>` 会永久丢消息**：PEL 里的消息不会被 `>` 再投递，必须有 `XPENDING` + `XCLAIM` 的补偿任务。
5. **毒消息堵队列**：老代码 `while(true)` 重读 pending，一条坏消息就把新消息全卡住。要"投递次数上限 + 死信 + ACK"。
6. **`tryLock()` 无参就直接放弃**：老代码抢不到锁就 `log.error` 然后 `return`，而调用方随后 ACK —— 订单凭空消失。现在抢不到锁抛可重试异常，消息留在 PEL。
7. **消费者同名**：多实例写死 `c1` 会让 PEL 记账混乱、互相认领。消费者名用 `hostname + uuid`。
8. **`XGROUP CREATE` 对不存在的 key 报错**：先塞占位消息造流，建组后删除。
9. **`XACK` 失败不影响正确性**：消息会留在 PEL 被重投，靠 `orderId` 幂等兜住，不会重复下单。
10. **JS 精度**：`redisIdWorker` 的订单号是 19 位，前端/压测脚本用 `Number` 解析会丢精度（`651609322635133000` 这种尾巴是 0 的就是丢精度了），展示用字符串。

## 13. 调参与上线注意

| 参数 | 现值 | 建议 |
|---|---|---|
| `SECKILL_PENDING_IDLE_SECONDS` | 60s | 取"单条最长处理耗时 × 3"以上；太小会抢走别人正在处理的消息 |
| pending 扫描周期 | 30s | 重试延迟上限 ≈ 阈值 + 周期 |
| `SECKILL_MAX_DELIVERY` | 5 | MTTR 短的业务可以给 3~5，越大死信越少但脏消息停留越久 |
| 消费者并发 | 容器默认（单线程轮询 × batch 16） | 落库是 IO 密集，可用 `executor(线程池)` 提高并发；注意 DB 连接池上限 |
| Stream 长度 | 未截断 | 建议 `XADD MAXLEN ~ 100000` 或定期 `XTRIM`，否则 Stream 会一直涨 |

上线后建议补的三个"运维动作"：

1. **库存对账**：定时比对 `DB stock + 未支付订单数` 与 `Redis stock`，不一致就告警（不要自动覆盖，容易把正在进行的秒杀打乱）；
2. **死信监控**：`XLEN stream.orders.dlq > 0` 就报警，人工确认是补单还是退款；
3. **PEL 水位监控**：`XPENDING` 的 total 持续 > 0 说明消费者处理能力不足或有毒消息。
