先给一句话把这五个问题串起来：**它们都在处理同一件事——在“检查”和“执行”这两步之间的间隙里，别人插了进来。** 所有方案的本质都是把这条缝隙挤掉：要么合成一个原子动作（Lua、单条 SQL、CAS），要么让动作可以重复做（幂等），要么让错误能自愈（补偿、TTL）。

## 一、轮换泄露检测：让“再次使用”变成泄露的证据

### 问题从哪来

access token 只有 30 分钟，泄露了损失有限，而且它不查 Redis、纯本地验签，图的就是快。

refresh token 有 7 天，它的唯一职责是“换新的 access”。**它是整个体系里唯一一个长期有效的凭证**。泄露了，攻击者可以连续 7 天不断换新 access，而且你完全不知道——因为正常用户也在用它，日志上看不出区别。

所以问题不是“怎么防泄露”，而是“**泄露了怎么发现**”。

### 轮换做了什么

每次来换 token，不只换 access，连这个长命的 refresh 也一起换新的，旧的立刻作废。

一句话：refresh token 从“长期通行证”变成了“**一次性车票**”。

### 为什么这能发现泄露（关键推理）

一张票用过就被剪掉。那如果**剪过的票又出现在检票口**，只有两种解释：

1. 有人复制了这张票 —— 真泄露
2. 客户端 bug / 网络重试把同一张票递了两次 —— 假警报

排除第 2 种，剩下就是泄露。

轮换最精妙的地方在这里：它不需要猜“攻击者在哪、用了什么”，而是让攻击行为**必然留下一次可观测的重复使用**。安全设计里，能把“不可见的风险”转化成“一个可见的信号”，就是巨大的进步。

### 你代码里的实现

[UserServiceImpl.java:242](tfshz/src/main/java/com/tfsh/Service/impl/UserServiceImpl.java#L242)：

```
1. 验签 + 校验 type=refresh    → 防伪造、防拿 access 冒充
2. 查 Redis 白名单 login:refresh:{userId}:{jti}
     有   → 删掉 jti，签新的一对，新 jti 写白名单
     没有 → 拒绝
3. 因为旧 key 被删了，第二次拿同一个 refresh 来换，必然落到"没有"这一支
```

### 但“检测”要变成“响应”，还差三步

你自己在注释里也标注了这点。这三步是“轮换”和“轮换泄露检测”的分界线：

**第一步：区分“过期、登出”和“被复用”。**
现在 `flag == null` 同时包含两种情况，分不清是正常退出还是被攻击。做法是轮换时**别直接删**，而是把旧 jti 的值改写成 `used`，TTL 保留到这个 token 原本的过期时间。这样再查时能读到“已用过”，才能确认是复用而不是过期。

**第二步：复用了就把整族作废。**
引入“会话家族”——同一次登录派生出的所有 refresh 共享一个 familyId。一旦发现复用，删掉这个 familyId 下**所有**有效 token，让攻击者和真实用户一起下线。

为什么这么狠？因为此刻你**无法分辨谁是攻击者**。攻击者可能抢先换过一次，那手里拿着旧票的就成了真实用户。安全上宁可错杀（代价是一次重新登录），也不能放长线。

**第三步：给网络重试留一条缝。**
客户端超时重试会误触发。做法是旧 jti 作废后保留 30 秒宽限窗口，窗口内再次使用就返回**同一个新 token**（把这次轮换结果缓存起来），既不报警也不签新的。

### 顺带两个风险点（说的时候要心里有数）

**① `logout()` 用了 `KEYS`**（[UserServiceImpl.java:287](tfshz/src/main/java/com/tfsh/Service/impl/UserServiceImpl.java#L287)）：

```java
Set<String> keys = stringRedisTemplate.keys(LOGIN_REFRESH_KEY + userId + ":*");
```

`KEYS` 是全库扫描，数据量大时会把 Redis 单线程卡住几百毫秒到几秒——秒杀场景下这是致命的。正确做法是用一个 `Set` 维护该用户的所有 jti，或者直接按 session family 存一个 key 整体删。

**② access 被踢后还能再用 30 分钟**。这是有意取舍，[RefreshTokenInterceptor.java](tfshz/src/main/java/com/tfsh/utils/RefreshTokenInterceptor.java) 的注释写了。要“秒级踢人”就得给 access 加黑名单，那就等于每个请求都查 Redis，双 token 的性能红利归零。这是取舍不是缺陷，关键是你知道自己选了哪一边。

## 二、逻辑过期、补偿重试、TTL 兜底、为什么不延迟双删

### 击穿到底是什么

不是“缓存里没数据”，而是“**没数据的那一瞬间，所有人同时去敲数据库的门**”。缓存的作用是挡住绝大多数请求，它一旦同时失效，闸门就开了。

### 两种堵法

**第一种：互斥锁。** 只放一个人进去查库，其他人在门口排队。问题是慢——用户得等。

**第二种：逻辑过期。** 思路是“**别让缓存真的消失**”。

具体做法是把存的东西换成一个信封：

```json
{ "data": <真正的数据>, "expireTime": "2024-01-01 10:30:00" }
```

这个 key 在 Redis 里**不设过期时间**。“是否过期”不看 Redis 的 TTL，而是看信封里自己写的 `expireTime`。

于是读的时候有三种情况：

| 情况           | 行为                                                   |
| -------------- | ------------------------------------------------------ |
| 信封没过期     | 直接用                                                 |
| 信封过期了     | **先返回里面的旧数据**，同时起后台线程查库、写回新信封 |
| key 完全不存在 | 才同步查库                                             |

**所以你的理解完全正确：就是“先给旧值，异步取新值”。**

### 为什么这能防击穿

因为请求**永远不会落到“缓存空了”这个状态**。

缓存里始终有东西可以拿，所以没有人需要排队等数据库，也就没有“同时敲门”这回事。核心不在“异步”，在于**把“空”换成了“旧”**。异步只是让你不用为这个“旧”多付延迟。

### 代价（要能主动说出来）

**① 一致性变弱。** 后台重建完成前的几百毫秒里，用户读的是旧数据。所以这方案只适合能容忍短暂陈旧的数据——你用在秒杀券列表，合适；用在库存、余额上就是灾难。

**② 并发重建。** 一堆线程同时发现过期，会同时起重建任务。所以还得加把锁，只有抢到的才真去查库。[CacheClient.java:72](tfshz/src/main/java/com/tfsh/utils/CacheClient.java#L72) 这一点你做对了。

**③ 你现在的 key 会永驻内存。** [CacheClient.java:121](tfshz/src/main/java/com/tfsh/utils/CacheClient.java#L121) 的 `set(key, json)` 没带 TTL。逻辑过期方案一般仍建议设一个远大于逻辑过期时间的物理 TTL 兜底，防止冷数据把 Redis 撑满。

### “删除失败由消息队列补偿重试”是什么意思

**先说为什么是“删除”。** 更新数据库后，如果去**更新**缓存，两个并发写可能以错误顺序落到缓存，留下一个谁也没想到的值。而**删除**没有顺序问题——删两次等于删一次，迟到的删除最多让人多回源一次。所以标准做法是“改库 → 删缓存”。

**但删除可能失败。** Redis 抖了一下、网络超时、连接池满了。这时数据库是新值，缓存是旧值，而且**它会一直错下去**，直到缓存自然过期。

补偿就是：删失败时，把“要删哪个 key”写进队列（你用的是 Redis Stream `stream.cache-delete`），由消费者异步重试删除。

[CacheDeleteCompensator.java](tfshz/src/main/java/com/tfsh/utils/CacheDeleteCompensator.java) 里有三个关键设计：

1. **消息里只放 key，不放数据。** 因为“删除”这个动作天然可以重复做，所以消息重复消费没有副作用。这是补偿能用队列实现的**根本原因**。如果放的是数据，重投就可能把旧数据又写回去。
2. **梯度退避**：1s、2s、4s……上限 60s，最多 10 次。避免失败瞬间密集重试，把 Redis 打得更死。
3. **重试用尽写 error 告警**，交人工。程序不能假装还能自愈。

### “TTL 兜底”是什么意思

**兜底 = 假设前面所有机制都失效了，还有最后一道保险。**

那道保险就是缓存 key 自己的过期时间。就算补偿消息丢了、消费者挂了、告警没人看——缓存里的旧值**到点会自己消失**，下次读自然去数据库拿新值。

所以它保证的不是“一定正确”，而是“**错误一定有上界**”：最坏情况下，不一致时长 ≤ 缓存 TTL。这就是“最终一致”里“最终”两个字的真实含义。你项目里 `CACHE_VOUCHER_TTL = 30分钟`，等于在承诺“最多错 30 分钟”。

### 为什么不延迟双删

延迟双删的做法是：改库前删一次 → 改库 → 睡 500ms~1s → 再删一次。

它要解决这么个窗口：A 删了缓存，B 来读发现空，去查库（A 还没提交，B 读到旧值），B 把旧值写回缓存，A 才提交——缓存里就留下旧值了，而且没人会再删它。第二次删除就是为了清掉 B 回填的那份。

它有三个问题：

**① sleep 的时间是猜的。** 得保证睡够“B 读库 + 回填”的耗时。但 B 可能刚好赶上 GC 或慢查询，sleep 多长都可能不够；sleep 太长又拖慢接口。**这个参数没有正确答案。**

**② 它只降低概率，不消除。** 第二次删除自己也可能失败，失败了就没人管了。

**③ 它阻塞线程。** sleep 期间那个请求占着线程什么也不干，高并发下直接吃吞吐。

你的项目用“补偿重试 + TTL”替代它，是因为这套方案**更强、可观测、不阻塞**：

- **强**：重试是确定性的，有次数、有退避、有告警；sleep 方案是“赌一次”
- **可观测**：每次重试都有日志，能知道哪条 key 一直删不掉
- **不阻塞**：全异步
- **有上界**：TTL 给了最坏情况的承诺，sleep 方案没有这个上界

### 但要说清它没解决的问题

补偿方案防的是“**删除动作失败**”，防不了“**删除成功之后又有并发读把旧值塞回来**”（就是上面 B 那个场景）。因为消息里只有 key，重试删一次就结束了。

严格治这个需要另外的手段：
- 给缓存值带上数据版本号，回填时比对版本，旧版本直接丢弃
- 或者订阅数据库 binlog（Canal）驱动删除——“数据库变了”这个事实是强一致的，不依赖业务代码记得发消息

所以你这套的定位是“**实用主义的最终一致**”，说的时候别说成“彻底解决”。

## 三、SETNX 幂等守卫：一张只放行一个人的闸口

### 先还原场景

[VoucherOrderServiceImpl.java:142](tfshz/src/main/java/com/tfsh/Service/impl/VoucherOrderServiceImpl.java#L142)：

```
抢券成功 → Redis 里 DECR 已执行、SADD 已执行（用户被标记为"已抢到"）
         → 要把订单丢进 Kafka 让消费者落库
         → 投递失败 → 库存减了，订单永远不会产生 → 这张券凭空消失
         → 必须把扣掉的那份退回去：INCR 库存、SREM 用户
```

这就是“回滚库存”。

### 为什么这里需要一个“守卫”

**因为“投递失败”这个判断本身是不可靠的。**

网络超时的时候你**不知道**消息到底有没有出去：

- 可能真没发出去 → 应该回滚
- 可能发出去了，只是回包丢了 → 不该回滚，消费者马上会建单

如果你回滚了，而消息其实发出去了，就变成：**库存退回去了 + 订单又生成了 → 超卖。**

还有第二种重复回滚来自异步链路本身：Kafka 是“至少一次”投递。消息可能被重投；如果消费者因为“数据库库存不足”或“用户已买过”而回滚了预扣，然后**在提交 offset 前崩了**，这条消息会再来一次，又回滚一遍 → 库存加两次 → Redis 库存虚高 → 超卖。

所以回滚必须满足：**同一个订单，不管触发多少次，库存只能退一次。**

### SETNX 干了什么

[SeckillStockRollback.java:54](tfshz/src/main/java/com/tfsh/seckill/SeckillStockRollback.java#L54)：

```java
Boolean first = stringRedisTemplate.opsForValue()
        .setIfAbsent("seckill:rolledback:" + orderId, "1", Duration.ofHours(24));
if (!Boolean.TRUE.equals(first)) {
    log.info("预扣已回滚过，跳过 orderId={}", orderId);
    return;   // 什么都不做
}
rollback(voucherId, userId);
```

`setIfAbsent` 就是 Redis 的 `SET key value NX`：**key 不存在时才设置成功（返回 true）；已存在就什么都不做（返回 false）**。

“查存在性”和“写入”在 Redis 单线程里**一步完成**，不存在“我查到不存在、刚要写、别人抢先写了”这个窗口。

于是有了一个**只放行第一个人的闸口**：第一个来的拿到 true，执行回滚；后面的所有人拿到 false，直接走开。

### 你的两个疑问

#### “我理解回滚库存是加了一个分布式锁吗”

底层确实是同一个原语——`SET NX` 就是分布式锁的零件。但**语义完全不同**：

|                | 分布式锁                                      | 幂等守卫                      |
| -------------- | --------------------------------------------- | ----------------------------- |
| 目标           | 让并发**排队**，一个一个来                    | 让动作**只做一次**            |
| 后来者         | **等着**，锁释放后进来执行                    | **直接放弃**，不执行          |
| 结束           | 用完要**主动释放**                            | **永不释放**，靠 TTL 自然过期 |
| 用在这里会怎样 | 锁释放后重投的消息还能再回滚一遍 → **不幂等** | 无论多少次只生效一次          |

一句话：**锁是“轮流进去”，守卫是“只准进一个，其余退回”。**

这是关键区别。如果用锁来实现回滚，锁一释放，下一次重投照样能再回滚 → 库存还是虚高。所以这里要的不是锁，是**一次性通行证**——而“一次性”的关键恰恰是**不释放**。

#### “幂等是多次操作结果一致，为什么叫幂等守卫”

你说得对，幂等是**目标**（多做几次，结果和做一次一样）。但这个目标不会自己实现——`INCR` 本身**不是**幂等的，执行两次就是加 2。

所以需要有个东西**在动作前面挡着**，把第 2 次、第 3 次挡在门外，让动作实际只被执行一次。这个“挡”的角色就是守卫。

叫“守卫”而不是“幂等”，是因为它实现幂等的方式是**拦截**，而不是让操作本身变得可重复。**幂等是它守护的东西，“守卫”是它干的事**——这个命名其实比叫“幂等标记”更准。

### 一处要修正你表述的地方

你的原话是“**预扣成功后若消息投递失败，通过 SETNX 幂等守卫回滚库存**”。

但看代码：投递失败那条路是**没有守卫**的：

```java
if (!seckillOrderPublisher.publish(codec.fromOrder(order))) {
    stockRollback.rollback(voucherId, user.getId());   // ← 无守卫
```

守卫加在**消费侧**（[SeckillOrderProcessor.java:47](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderProcessor.java#L47)、[52](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderProcessor.java#L52)）：

```java
case USER_DUPLICATE  -> stockRollback.rollbackOnce(order.getId(), ...);   // ← 有守卫
case STOCK_EXHAUSTED -> stockRollback.rollbackOnce(order.getId(), ...);
```

而投递失败这条路有个残留风险：[KafkaSeckillOrderPublisher.java:39](tfshz/src/main/java/com/tfsh/seckill/mq/KafkaSeckillOrderPublisher.java#L39) 用的是 `kafkaTemplate.send(...).get(3, TimeUnit.SECONDS)`。**客户端 3 秒超时，不代表 broker 没收到。** 如果消息其实进了 Kafka，你这边判定失败并回滚，消费者随后照样建单 → 库存退了一次、订单也生成了 → 超卖。

所以更准确的说法是：**SETNX 守卫保护的是“消费侧的重复投递”，防不住“发送超时但实际成功”这种歧义。** 后者的正确解法不是加守卫，而是：
- 让 Kafka 的 `enable.idempotence=true` + `acks=all`（你已经配了）把重复**消息**去掉
- 对“回滚了但订单后来出现”的情况做**延迟对账**：一定时间后检查“回滚过的 orderId 是否真的存在订单”，存在就补扣库存
- 或者把“这笔预扣的最终命运”做成一条可查询的决策记录，两侧都读它

这段讲清楚，比笼统说“用 SETNX 保证幂等”要扎实得多。

## 四、条件更新、唯一索引、分布式锁：三层放一起才叫兜底

这三个经常被混着说，其实管的是**两件不同的事**：超卖（库存卖多了）和重复单（同一个人买了多份）。

### 一、唯一索引 → 管“重复单”

就是数据库表上的一个约束：

```sql
UNIQUE KEY uk_user_voucher (user_id, voucher_id)
```

意思是：**“同一个用户 + 同一张券”这个组合，库里只能出现一次。**

关键在它的可靠性来自哪：不是应用层判断，不是 Redis，是**存储引擎的索引结构**。两个事务同时插入同样的 `(user, voucher)`，InnoDB 在索引上排队，第二个必然失败。

你代码里就是这么兜的（[SeckillOrderPersistService.java:102](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderPersistService.java#L102)）：

```java
try {
    voucherOrderMapper.insert(order);
} catch (DuplicateKeyException e) {
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    return PersistOutcome.USER_DUPLICATE;
}
```

注意 catch 之后还要**把整个事务标记为回滚**——因为在这之前已经扣过库存了，插入失败必须把扣减一起撤掉。

这是整个体系里**最硬的一道防线**：不依赖应用逻辑正确、不依赖锁没失效、不依赖消息不重复。哪怕前面全错了，它也拦得住。

### 二、条件更新 → 管“超卖”

对比两条 SQL：

```sql
-- 错的（盲减）
UPDATE seckill_voucher SET stock = stock - 1 WHERE voucher_id = 1001;

-- 对的（条件更新）
UPDATE seckill_voucher SET stock = stock - 1 WHERE voucher_id = 1001 AND stock > 0;
```

差的就那一个 `AND stock > 0`，但它是本质区别。

错误写法的问题是：**它压根不看当前库存是多少。** 库存是 0，它照样减，减成 -1、-2。这叫“把检查交给别人”。

正确写法的关键是：**“判断库存够不够”和“把库存减掉”写在了同一条语句里。** 数据库执行这条 UPDATE 时锁住这一行，在锁的保护下完成“看 stock 是不是 > 0 → 是就减”。中间没有缝隙给别人插进来。

然后看返回值（[StockService.java:53](tfshz/src/main/java/com/tfsh/order/StockService.java#L53) 末尾那个 `.update()`）：**影响行数 1 = 扣成功，0 = 条件没满足（库存没了）**。业务就靠这个布尔值分流。

这就是超卖的标准解法：**让数据库保证“不会减成负数”，而不是在 Java 里写 `if (stock > 0) stock--;`**——后者在并发下一定出事，因为 `if` 和 `--` 之间隔着一个“可以被别人插队”的空档。

### 三、分布式锁 → 管“串行化”，但它不可信

`SET lock:xxx 1 NX PX 3000`，只有一个人能拿到，其他人在门外等。

它解决的问题是：有些操作**不是一条 SQL 能说完的**。比如落库这段（[SeckillOrderPersistService.java:79](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderPersistService.java#L79) 起）：

```
1. 查这个用户有没有买过
2. 扣库存
3. 插订单
```

两个消息同时处理同一用户同一张券，可能**同时**通过第 1 步检查（都查到“没买过”），然后都往下走。锁把这段串起来，让第二个等第一个走完，这样它第 1 步就能看到对方插的记录了。

**但锁的致命问题是：它可能失效。**

- 锁过期了业务还没跑完（GC 停顿、慢查询）→ 两个人同时在临界区
- Redis 主从切换，锁丢在还没同步的从节点 → 两个人同时拿到
- 网络分区 → 客户端以为自己拿到锁了

这些不是虚构，是实践中都会发生的。所以业界共识是：**分布式锁只能用来减少冲突、优化性能，不能当作正确性的最后依靠。**

### 四、三者怎么配合——这是最该讲清的部分

一套**分层防御**，从快到慢、从“不可信”到“绝对可靠”：

| 层   | 手段                                                         | 挡住什么                       | 靠谱程度                      |
| ---- | ------------------------------------------------------------ | ------------------------------ | ----------------------------- |
| 1    | Redis + Lua（[seckill.lua](tfshz/src/main/resources/lua/seckill.lua)） | 99% 的无效流量，压根不碰数据库 | 快，但数据可能在 Redis 里算错 |
| 2    | Redisson 锁                                                  | 把同一用户的落库串行化         | **可能失效**                  |
| 3    | 条件更新 `WHERE stock > 0`                                   | 库存不会变成负数               | 数据库保证                    |
| 4    | 唯一索引 `(user_id, voucher_id)`                             | 不出重复单                     | 数据库保证，最硬              |

**“兜底”这个词的含义就在这里**：前面三层都建立在“假设”上——假设 Redis 没挂、假设锁没失效、假设消息不丢、假设代码逻辑对。**兜底就是假设前面全错了，最后这一层仍然不能让数据出错。**

背后的第一性原理是一句话：**正确性不能建立在“大概率不出错”的组件上。**

分布式系统里，凡是“先检查、再执行”（check-then-act）的地方都有一道竞争窗口。唯一安全的是**把检查和执行合并成同一个原子动作**的地方——数据库的唯一索引（插入时索引冲突检测）和条件更新（行锁下判断+修改），恰好就是这样的地方。所以整个系统的**信任锚点必须落在数据库**，前面几层只是为了让数据库别被压垮。

顺序上也是这个道理：**越贵的越靠后**。Redis 快但不可信，数据库可信但慢。让快的地方挡掉绝大多数，只让极少数真正需要裁决的请求到达慢的地方。

### ⚠️ 这里有个必须补的窟窿

你的代码注释里反复提到“唯一索引 `uk_user_voucher` 兜住一人一单”——[SeckillOrderPersistService.java:31](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderPersistService.java#L31)、[104](tfshz/src/main/java/com/tfsh/seckill/SeckillOrderPersistService.java#L104)、[SeckillOrderKafkaListener.java:24](tfshz/src/main/java/com/tfsh/seckill/mq/SeckillOrderKafkaListener.java#L24)。

也就是说：**注释宣称的“最硬的一道防线”，目前可能根本不存在。**

这必须补上，否则前面三层一旦都失效（Redis 被清 + 消息重投 + 锁过期），就真的没人兜了：

```sql

```

执行前先查一遍历史数据有没有重复，否则加索引会直接失败：

```sql
 GROUP BY user_id, voucher_id HAVING c > 1;
```

## 五、版本号 CAS 乐观锁 + 重试

先回答你两个判断：

> **“是不是在数据库端兜底的”** → **对，而且这是关键。**

它的正确性来自数据库行锁：`UPDATE` 锁住这一行，在锁的保护下完成“看 version 是不是 5 → 是就改成 6”。不依赖 Redis、不依赖应用层、不依赖分布式锁。所以不管前面用了什么，这一步都兜得住。

> **“采用 CAS 状态机，只能由未支付变成已支付”** → **方向完全对，但有三处要修正。**

### 先还原竞争

定时任务（[OrderTimeoutTask.java](tfshz/src/main/java/com/tfsh/task/OrderTimeoutTask.java)）每 60 秒扫一次，捞出“状态 = 待支付 且 已过支付截止时间”的订单，准备关单并回补库存。

与此同时用户刚好付完钱，支付回调准备把状态改成已支付。

两个操作**都先读到“状态 = 待支付”**，然后都去写。可能的结果：

- 订单被关了，但用户付了钱 → **钱收了，货不给**（最严重）
- 订单改成已支付了，但库存被回补了 → **同一张券卖给了两个人**（超卖）

这个问题的学名是“**丢失更新**”：后写的把先写的覆盖掉，而且双方都以为自己基于最新数据。

### CAS 怎么解决

写的时候不是“直接改”，而是“**如果还是我看到的那个版本，才允许改**”：

```sql
UPDATE tb_voucher_order
   SET status = 4, version = version + 1, close_time = NOW()
 WHERE id = 123
   AND status = 1     -- 必须还是"待支付"
   AND version = 5    -- 必须还是我读到的版本
```

`WHERE` 在**比较**，`SET` 在**写入**。两个字合成一个原子动作，就是 CAS。

结果只有两种：

- **影响 1 行** → 中间没人动过，改成功了
- **影响 0 行** → 有人先改了，我这次不算数

你代码里的 `casStatus`（[VoucherOrderServiceImpl.java:423](tfshz/src/main/java/com/tfsh/Service/impl/VoucherOrderServiceImpl.java#L423)）就是这个：

```java
LambdaUpdateWrapper<VoucherOrder> wrapper = Wrappers.<VoucherOrder>lambdaUpdate()
        .eq(VoucherOrder::getId, orderId)
        .eq(VoucherOrder::getStatus, expectStatus)            // 状态没变
        .eq(VoucherOrder::getVersion, current.getVersion())   // 版本没变
        .set(VoucherOrder::getStatus, targetStatus)
        .setSql("version = version + 1");
if (update(wrapper)) { return true; }
```

### “重试”在这里到底是什么

这一点很关键：**重试不是“失败了再试到成功”，而是“重新读一次最新状态，重新做一次业务判断”。**

看 `casStatus` 的循环（第 425 行）：每次重试第一步都是 `getById(orderId)` **重新读**。拿到新数据后，第 427 行先判断：

```java
if (current == null || current.getStatus() != expectStatus) {
    return false;   // 状态已经不是我以为的样子 → 放弃，不重试了
}
```

**这一行才是真正解决问题的地方。** 它的意思是：

- 关单任务重试时读到**已支付** → 返回 false，**放弃关单，绝不回补库存**
- 支付回调重试时读到**已关闭** → 返回 false，上层据此决定报错还是退款

所以乐观锁的价值不只是“防止覆盖”，更重要的是：**让竞争失败的那一方有机会看到对方的决定，从而做出正确的业务响应。** CAS 只负责“我不会覆盖别人”，业务逻辑负责“看到别人的结果后我该干什么”。

### 三处要修正你的表述

#### 修正一：不只是“未支付 → 已支付”这一条边

准确说是“**状态机只允许特定的迁移**”，每条边都是一次 CAS。你项目的状态（[OrderStatus.java](tfshz/src/main/java/com/tfsh/order/OrderStatus.java)）有四条边：

| 从        | 到        | 触发者                                        |
| --------- | --------- | --------------------------------------------- |
| 待支付(1) | 已支付(2) | 支付回调 `confirmPaid`                        |
| 待支付(1) | 已关闭(4) | 超时关单 / 用户取消                           |
| 已支付(2) | 已核销(3) | 扫码核销 `verifyByCode`                       |
| 已支付(2) | 退款      | **你没有实现**（`refundTime` 字段存在但没用） |

要拒绝的是两类：

1. **从终态出发的迁移**（已关闭 → 已支付）——最危险的方向
2. **重复的同向迁移**（已支付 → 已支付）——重复的支付回调

第 2 类顺便就做了**幂等**：重复回调第二次 CAS 影响 0 行，代码走到 `latest.getStatus() == PAID` 分支返回成功（[VoucherOrderServiceImpl.java:255](tfshz/src/main/java/com/tfsh/Service/impl/VoucherOrderServiceImpl.java#L255)），用户看到的是“支付成功”而不是报错。这个细节很好，值得单独讲。

#### 修正二：不一定非要独立的 version 字段

很多实现直接用状态自己当 CAS 条件（`WHERE status = 1`），不引入 version。这在业务上更直观，而且天然幂等。

你两样都用了（`AND status = 1 AND version = 5`），也有道理：

- 只用 status：能防“状态被并发改”
- 加上 version：还能防“状态没变，但别的字段（payTime、verifyCode）被并发改了”

代价是 CAS 冲突率略高（任何字段改动都 bump version）。对订单表冲突本来就少，这个代价可以接受。

#### 修正三（最重要）：CAS 保证了“状态不乱”，但没保证“业务不吃亏”

假设关单任务先赢：

```
14:59:59  用户在支付渠道付了钱（渠道侧已成功）
15:00:00  关单任务 CAS 成功 → 订单关闭，库存回补
15:00:01  支付回调到达 → CAS 失败 → 你代码返回"订单已超时关闭，支付未生效"
```

**数据是一致的**（订单确实关了，库存确实回补了，不会超卖），但**用户被扣了钱却没拿到货**。

CAS 解决的是“数据不会自相矛盾”，解决不了“钱和货的对应关系”。

你代码里只是 `log.warn`（第 252 行）然后返回失败——演示项目可以，生产环境必须接上**退款**：支付回调 CAS 失败、且查到渠道已收款时，自动发起退款。这也是为什么我说状态机上“已支付 → 退款”那条边是缺的。

所以更完整的表述是：**CAS 保证状态机不被破坏，资金上的补偿要靠退款链路补上。** 面试时主动说出这一层，比只说“用 CAS 解决了并发”值钱得多。

### 还有一层保险：别只信本地状态

纯靠本地状态判断有个漏洞——**支付渠道的回调可能延迟**。用户付了，但通知还在路上，此时本地状态还是“待支付”，关单任务会把它误关。

稳妥做法是关单前**主动去支付渠道查一次最终状态**（你代码里 `payService.queryPaid` 有这个能力，但关单路径没调用），确认真的没付款再关。这叫“不信任本地状态，以渠道事实为准”。

## 收尾：我把这五层的共同结构画成一张图

```
                    请求进来
                       │
     ┌─────────────────▼─────────────────┐
     │ 第1层 原子动作（快，不可信）        │  Lua / 单条 SQL / CAS
     │ 把"检查+执行"缝死，不留插队窗口     │
     └─────────────────┬─────────────────┘
                       │ 少数漏过来
     ┌─────────────────▼─────────────────┐
     │ 第2层 幂等（让重复没有副作用）      │  SETNX 守卫 / 删除天然幂等 / CAS 幂等
     │ 同一件事做 N 次 = 做 1 次          │
     └─────────────────┬─────────────────┘
                       │ 仍然可能出错
     ┌─────────────────▼─────────────────┐
     │ 第3层 补偿（让错误能自愈）          │  MQ 重试 / 退避 / 告警
     │ 假设失败会发生，并给它一条退路      │
     └─────────────────┬─────────────────┘
                       │ 补偿也失败
     ┌─────────────────▼─────────────────┐
     │ 第4层 兜底（给错误一个时间上界）    │  TTL 过期 / 数据库唯一索引和条件更新
     │ 假设前面全错了，这里也不能错        │
     └───────────────────────────────────┘
```

**第 1 层和第 4 层是“硬”的，第 2、3 层是“软”的。** 面试里最容易被追问的，就是“你的软层失效了怎么办”——答案永远指向第 4 层。你现在第 4 层里的 `uk_user_voucher` 是空的，这是最该先补的一块。
