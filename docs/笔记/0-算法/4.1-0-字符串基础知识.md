从第一性原理来看，String、StringBuffer、StringBuilder 和 char[] 的根本分歧只有一个：**"字符序列"这块内存，是"只读一次、永久共享"，还是"可反复涂改"?** 这一个选择，决定了它们的可变性、线程安全、性能表现和适用场景。

---

## 第一层基石：字符与编码——为什么底层不是"字符串"，而是"字符数组"

计算机里没有"字符串"这个原初概念，只有**字节**和**编码规则**。一个字符（如 `'A'` 或 `'中'`）在内存中需要被表示为一个或多个字节。

Java 的 `char` 是 **16 位无符号整数**（UTF-16 编码单元），固定占 2 字节。这意味着 Java 在语言层面把"字符"抽象成了一个定长的基本类型，而**多个 char 依次排列，就构成了 char[]**。

所以，**char[] 是所有字符串类型最底层的物理载体**：String、StringBuilder、StringBuffer 在 JDK 8 及以前，内部存储的都是 `char[] value`。JDK 9 之后 String 和 AbstractStringBuilder 改为 `byte[] value` + 编码标识（Latin-1 或 UTF-16），目的是节省内存——纯英文场景下每个字符只需 1 字节而非 2 字节。但**抽象逻辑不变**：它们仍然是在管理一个"字符序列的存储数组"。

> **补充知识：char 不等于 Unicode 码点。** 一个 Unicode 码点（code point）可能由两个 char 组成（代理对 surrogate pair），例如 emoji 😀 在 Java 中 `length()` 返回 2。这是字符层面容易忽略的细节，但在字符串操作中会影响 `substring`、`charAt` 等方法的语义。

---

## 第二层：char[]——裸数组的代价

`char[]` 是最原始、最高效的字符存储方式：

- **可变**：`arr[0] = 'X'` 直接改写内存；
- **无封装**：调用方拿到引用后可以随意修改、越界、传 null；
- **无任何"字符串语义"**：不知道长度边界（只有 `arr.length` 这个物理容量）、不能自动扩容、不能拼接、不能比较内容。

从第一性原理看，char[] 是**"能力最强但约束最少"**的形态。正因为它太裸，直接暴露给业务代码会带来安全和正确性问题，Java 才需要在它之上构建带约束的抽象——这就是 String、StringBuilder、StringBuffer 存在的理由。

---

## 第三层：String——"写时复制、永久共享"的只读视图

### 不可变性的真正来源

String 的核心设计是：**一旦创建，它所引用的字符内容永不改变**。

```java
public final class String {
    private final char[] value;   // JDK 8；JDK 9+ 为 byte[]
    // 没有任何方法修改 value 中的元素
}
```

关键在于 **`private`** 和 **"不暴露修改方法"**，而不仅仅是 `final`。`final` 只保证 `value` 这个引用不指向别的数组，但数组内部的元素在技术上是可以被改写的；String 的不可变性来自 SUN 工程师在**所有 String 方法中刻意不触碰底层数组元素，并且不向外界暴露 value 引用**。`String` 类本身也被 `final` 修饰，禁止子类破坏这一契约。

### 由此衍生的连锁效应

**① 字符串常量池成为可能。** 既然字符串永不变，JVM 就可以安全地让多个引用共享同一个字符串实例。字面量 `"abc"` 会先查常量池，存在则直接复用地址；`new String("abc")` 则在堆中创建新对象，常量池中仍保留原实例。没有不可变性，共享就是危险的——任何一个引用修改了内容，所有共享者都会"中毒"。

**② 天然线程安全。** 不可变对象被多个线程同时读取时，无需任何同步。String 的线程安全是"免费"的。

**③ hashCode 可缓存。** String 在第一次调用 `hashCode()` 后会把结果缓存下来，后续作为 HashMap 的 key 时无需重新计算，这是 String 被广泛用作 Map key 的重要原因。

**④ 安全性。** 类加载、数据库连接、网络主机名等场景中，字符串作为参数传递时，如果可被中途篡改，会造成严重安全漏洞。不可变性堵住了这条路。

### 代价：每次"修改"都是"新建"

`String s = "a"; s = s + "b";` 在底层并不会在原对象上追加，而是创建一个新的 String 对象，让 `s` 指向它，旧的 `"a"` 等待 GC。在循环中大量拼接时，会产生海量短命对象，性能急剧下降。

## 第四层：StringBuilder——"可涂改的容器"

### 设计翻转：从"不可变"到"可变"

StringBuilder 的核心转变是：**底层数组不再是 `final` 的，且直接提供修改数组内容的接口**。它继承自 `AbstractStringBuilder`，后者持有 `char[] value`（无 `final`）和 `int count`（实际字符数），`append` 直接在原数组上写入，不创建新 String 对象。

```java
abstract class AbstractStringBuilder {
    char[] value;   // 可变，无 final
    int count;      // 实际长度
    // append 等方法直接修改 value 和 count
}
```

### 扩容机制

当 `count + 新增长度 > value.length` 时，触发扩容：

> **新容量 = 旧容量 × 2 + 2**

如果仍然不够，则直接取所需的最小容量。扩容的本质是 `Arrays.copyOf`（底层调用 `System.arraycopy`），即**申请一块更大的新数组，把旧数据拷过去，丢弃旧数组**。所以频繁扩容仍然有拷贝成本，**如果能预估最终长度，使用 `new StringBuilder(initialCapacity)` 可以显著减少扩容次数**。

### 非线程安全

StringBuilder 的 `append`、`delete` 等方法**没有加任何同步**。在单线程环境下这是最优选择，因为省去了锁的获取与释放开销；在多线程共享同一个 StringBuilder 实例并发写入时，会出现数据竞争，导致数据错乱。

---

## 第五层：StringBuffer——"加了锁的 StringBuilder"

StringBuffer 与 StringBuilder 的底层存储和扩容机制完全相同，都继承自 `AbstractStringBuilder`，区别只在一处：**StringBuffer 在需要保证线程安全的方法上加了 `synchronized` 关键字**。

```java
// StringBuffer
@Override
public synchronized StringBuffer append(String str) { ... }

// StringBuilder
@Override
public StringBuilder append(String str) { ... }   // 无 synchronized
```

这意味着同一时刻只能有一个线程进入 StringBuffer 的修改方法，从而保证多线程下的操作串行化、数据一致。

**代价是性能。** 即使在没有实际竞争的单线程场景下，`synchronized` 仍然涉及偏向锁/轻量级锁的状态维护；一旦出现竞争，则升级为重量级锁，开销更大。实测中 StringBuilder 在单线程拼接上的吞吐量显著高于 StringBuffer。StringBuffer 还有一个额外的 `toStringCache` 字段，用于缓存 `toString()` 的结果以避免重复拷贝，这是它在 JDK 1.0 时代留下的优化痕迹。

## 全维度对比与选型原则

| 维度             | String                            | StringBuilder            | StringBuffer         | char[]                                  |
| ---------------- | --------------------------------- | ------------------------ | -------------------- | --------------------------------------- |
| **可变性**       | 不可变                            | 可变                     | 可变                 | 可变                                    |
| **线程安全**     | 安全（靠不可变）                  | **不安全**               | 安全（synchronized） | 不安全                                  |
| **"修改"的成本** | 新建对象                          | 原地修改，均摊 O(1)      | 原地修改 + 锁开销    | 原地修改                                |
| **扩容**         | 不适用                            | 旧×2+2                   | 旧×2+2               | 手动管理                                |
| **封装性**       | 完整                              | 完整                     | 完整                 | **无**                                  |
| **典型用途**     | 常量、少量拼接、Map key、参数传递 | **单线程拼接（最常用）** | 多线程共享可变字符串 | 极底层、与 native/IO 交互、需要极致控制 |

### 选型决策树（从第一性原理推导）

**问题一：这个字符序列的内容需要改变吗？**

- **不需要** → 用 **String**。不可变带来共享、线程安全、可缓存 hash，收益全部拿到。
- **需要** → 进入问题二。

**问题二：修改是"一次性替换"还是"多次增量拼接"？**

- **一次性替换/少量操作** → String 仍然可用（`substring`、`replace` 返回新 String），代码更简洁，现代 JVM 的 GC 对短命对象也相对友好。
- **多次增量拼接（循环、流式构建）** → 用 **StringBuilder**（单线程）或 **StringBuffer**（多线程共享）。

**问题三：是否有多线程同时修改同一个可变字符串实例？**

- **否** → **StringBuilder**。这是 99% 的场景。
- **是** → **StringBuffer**。但需要知道，现代 Java 中更常见的做法是**在每个线程内用 StringBuilder 拼接，最后合并**，而不是共享一个 StringBuffer——锁竞争往往比拷贝更贵。

**char[] 的定位**：业务代码几乎不应直接使用裸 char[] 来充当"字符串"。它只在需要与底层 API（如 `java.io`、JNI、密码学库）交互，或需要手动管理内存布局时才会出场。一旦拿到 char[]，你就失去了 String 的所有安全约束。

## 补充你需要知道的关键知识

**1. `+` 字符串拼接的编译期魔法。** 在 Java 中，`"a" + b + "c"` 在编译期会被优化为 `StringBuilder`（JDK 9+ 为 `invokedynamic` + `StringConcatFactory`）的 append 链。所以**单个表达式中的 `+` 拼接并不慢**；慢的是**在循环中反复用 `+`**，因为每次循环都会新建一个 StringBuilder（或等效对象）再 `toString()`。

**2. `StringBuilder` 与 `String` 的互转有成本。** `sb.toString()` 会新建一个 String 并拷贝底层数组；`new StringBuilder(string)` 也会拷贝。在性能敏感的路径上，要尽量减少这种往返。

**3. `String.intern()` 是把堆中字符串"登记"到常量池的手段。** JDK 7+ 中，如果常量池中已有内容相等的字符串，`intern()` 返回池中引用；否则将堆中对象的引用放入池中（JDK 6 是复制对象进永久代）。它是用可控的内存换引用相等性判断的一种手段，但不应滥用。

**4. 不可变不等于"绝对无法修改"。** 通过反射可以强行改写 String 内部的 `value` 数组，但这会破坏常量池共享语义，带来不可预期的后果，生产代码中不应这样做。

**5. JDK 9+ 的 `byte[]` 优化不改变抽象契约。** String 和 StringBuilder/StringBuffer 的底层从 char[] 切换为 byte[] + coder，纯粹是为了压缩纯 Latin-1 字符串的内存占用（每字符 1 字节而非 2 字节），**不可变性、线程安全性、扩容逻辑的语义完全不变**。

**一句话收束：** char[] 是"裸内存"，String 是在裸内存上加了一层**"永不修改、可以安全共享"**的契约，StringBuilder 和 StringBuffer 则是**"允许修改"**的容器——前者信任调用方在单线程内使用，后者用锁替调用方兜底。理解了这一层取舍，四者的所有行为差异都可以被推导出来。
